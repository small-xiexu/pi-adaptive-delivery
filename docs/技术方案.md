# Pi Adaptive Delivery 技术方案

## 1. 文档状态

- 状态：已确认
- 目标仓库：`small-xiexu/pi-adaptive-delivery`
- 目标产物：可通过 Git 或 npm 安装的 Pi Package
- 当前阶段：R29 Package 修复与限定复审已完成，等待恢复第七轮亚马逊真实 TUI canary
- 初始兼容性基线：Pi `0.84.4`、bundled `pi-subagents` `0.64.0`

本文件定义产品边界、运行状态、组件职责和验收标准。技术方案已经用户复审确认；实施计划再次确认后，才允许开发 Package。

## 2. 背景与问题

用户希望使用 Pi 完成长期、可恢复、质量受控的软件开发。目前通过多个独立 Pi 窗口手工复制提示词，在架构师、开发 Agent 和测试 Agent 之间传递任务。这种方式有以下问题：

- 需求、方案、代码版本和测试结论容易错位。
- 多个窗口可能同时修改同一工作区，测试面对的是移动目标。
- 长对话和手工转述会丢失已确认决策。
- 开发 Agent 与测试 Agent 如果使用相同模型和相似上下文，盲点仍然相关。
- Agent 声称“测试通过”不能替代真实命令的运行证据。
- 固定三 Agent 流程会给低风险小改动带来不必要的成本。

目标方案采用一个长期父 Pi 会话作为中央编排者，复用 `pi-subagents` 启动受控子 Agent，并通过风险分级 Delivery Contract、用户授权、真实测试和按需 fresh review 建立完整交付闭环。

## 3. 目标

### 3.1 产品目标

- 所有会修改仓库状态的开发任务，在修改前都必须具备可解析并绑定当前 Session/workspace 的 Delivery Contract；persistent project documentation 按风险启用。
- 流程阶段固定，但方案深度、确认次数、Agent 数量和验证范围根据复杂度、风险与不确定性自适应。
- 用户始终拥有需求、产品、范围、架构授权和发布决策权。
- 获得实施授权后，父会话能够持续编排到开发交付；遇到未授权决策或阻塞时必须暂停。
- Package 能跨项目复用，并服从每个项目自己的 `AGENTS.md`、事实源、计划台账和验证命令。

### 3.2 工程目标

- 保持一个中央编排者和每个工作区一个写入者。
- 使用真实宿主机验证命令作为确定性门禁。
- 使用 fresh-context reviewer 提供独立语义审查。
- 保存审批状态、运行记录和恢复信息，支持 Session 恢复、分支和 compaction。
- 模型和推理等级由用户配置，不在 Package 中硬编码 Provider 或模型 ID。
- Package 结构保持最小，不重复实现 `pi-subagents`、计划系统、CI 或发布系统。

## 4. 非目标

- 不训练、微调或自动更新任何模型权重。
- 不允许 Package 自动修改自己的 Prompt、Skill、Extension 或配置并立即生效。
- 不模拟完整“AI 软件公司”，不固定为架构师、开发、测试三个长期窗口。
- 不重新实现子 Agent 进程、Mission、Fleet、worktree、通用 acceptance runtime 或 CI；固定验证器只顺序执行当前 plan 已批准的命令。
- 不替代项目的 Issue、TODO、实施计划或技术事实源。
- 不自动 commit、push、创建 PR、发布 npm、部署或操作生产环境。
- 不把 Pi 进程内权限控制描述为操作系统沙箱。
- 不自动上传源码、会话、运行制品或指标。

## 5. 核心不变量

1. 没有职责完整且 runtime 可解析的 Delivery Contract，不得进入实现阶段。
2. 没有用户通过 TUI 作出的可验证修改授权，不得产生仓库写入。
3. 自适应只能调整流程仪式，不能绕过授权、单 writer、scope、candidate 和真实验证。
4. 技术方案必须基于当前代码、配置、测试和事实源，不得只依据对话推测。
5. 同一个 cwd 或 worktree 同时只能有一个写入者。
6. reviewer 必须读取原始需求、验收标准和 runtime 生成且绑定 candidate 的 actual diff，不能只依赖 worker 总结或 hash。
7. 子 Agent 报告的测试结果只是声明；只有 runtime 执行并记录的命令才是 verified evidence。
8. 需求、范围或架构发生实质变化时，必须使已有批准失效并退回相应阶段。
9. 项目规则优先于 Package 默认值；Package 不为项目补写关键业务决策。
10. 开发交付不自动包含提交、推送、PR、发布或部署。
11. 技术方案和实施计划的批准只绑定当前 Session 中不可变的消息条目，不批准可变文件或 runtime artifact。
12. runtime gate、review 和最终工作区绑定 candidate digest；项目进度制品在交付前现场读取并参与最终检查，相关候选变化后旧证据立即失效。
13. 项目进度继续服从项目自己的计划、Issue 或 TODO 规则；Extension 只持久化运行时断点，并在 writer-free 的可证明边界触发项目进度回写。
14. Standard/High-Risk 的技术方案和实施计划必须在源码实现前同步为目标项目中的需求级文档；Tiny 只保存 Session/runtime contract。路径先服从用户与项目规则，Package 默认值只补空白。

## 6. 适用范围

### 6.1 进入交付流程的任务

- 业务代码、测试、配置和构建脚本修改
- API、数据结构、数据库迁移和工作流修改
- 前端交互、视觉样式和用户流程修改
- 会改变当前行为、接口或运维方式的文档修改
- 缺陷修复、重构和紧急修复

### 6.2 不进入实现状态的任务

- 纯问答、只读研究、诊断和代码评审
- 未获得修复或实现授权的故障排查
- 只产生建议、不修改项目文件的架构讨论

这些请求保持 `IDLE`，不得调用 `delivery_begin`。只有用户明确输入 `/delivery-shape` 才通过 Pi 模板展开前的原始 `input` 事件一次性授权本回合启动流程；只读任务一旦转为修改请求，先由用户使用 `/delivery-shape <需求>` 从技术方案阶段进入本流程。

## 7. 自适应判断模型

父会话从复杂度、风险和不确定性三个维度作出可见判断。该判断是架构师建议，不实现封闭评分器；用户可以覆盖判断。

### 7.1 复杂度

- 小型：局部改动、影响路径单一、无共享契约变化。
- 中型：多文件或单模块内跨层修改，需要新增或调整测试。
- 大型：跨模块、跨前后端、涉及公共契约或需要分里程碑交付。

### 7.2 风险

- 低风险：局部、可逆、测试充分，不涉及权限和持久化数据。
- 中风险：共享组件、外部接口、用户流程或兼容行为发生变化。
- 高风险：认证、授权、租户隔离、密钥、费用、迁移、删除、并发、生产或不可逆操作。

### 7.3 不确定性

- 需求是否存在未决产品选择。
- 当前实现和文档是否一致。
- 失败是否可稳定复现。
- 验收标准是否可执行。

风险优先于代码量。一行权限修复仍按高风险处理；大型但机械的生成改动不自动升级为高风险设计。

## 8. 角色与权限

Agent 发现、配置、状态制品和编排参数始终使用稳定英文角色标识；面向用户的 TUI、`/delivery-status`、通知和文档使用中文主名称，并保留英文标识用于配置与诊断。用户和父会话是治理角色，不注册为子 Agent。

| 角色 | 职责 | 默认权限 |
|---|---|---|
| 用户 `[User]` | 产品决策、范围确认、方案批准、实施授权、发布授权 | 唯一批准者 |
| 中央架构师 `[父 Pi 会话]` | 产品与技术架构、任务分类、中央编排、发现裁决、最终交付 | 未批准前只读；批准后按项目授权工作 |
| 代码侦察员 `[scout]` | bundled runtime 通用代码侦察角色；当前 Delivery 流程不公开，普通取证由父 Pi 完成 | 不进入当前流程 |
| 资料研究员 `[researcher]` | 官方文档、规范和外部证据 | 预留角色；v0.1 strict pre-approval 因 `denyExtensions:true` 不启用 |
| 架构顾问 `[oracle]` | 高风险方向挑战和关键取舍审查 | 只读，不作最终决定 |
| 开发执行者 `[worker]` | 当前里程碑实现和开发期自检 | 唯一写入者 |
| 独立审查员 `[reviewer]` | 对实际 diff 作 fresh-context 独立审查 | 只读 |
| 固定验证器 `[Delivery Gate validator]` | 通过 Pi 公开命令 API 顺序执行并展示批准命令 | 只执行已批准 plan contract |
| 变更监视器 `[Watchdog]` | 在安全边界补充范围和改动审查 | 补充证据，不替代正式验收 |

父会话保留最终裁决权。任何子 Agent 都不得扩大产品范围、批准方案、启动发布或把自己的检查结果视为交付授权。

## 9. 方案与计划契约

Delivery Contract 与 persistent project documentation 解耦。所有修改任务都有机器可解析、由 Session assistant entry 承载并经 TUI 批准的 contract；只有 Standard/High-Risk 使用需求级技术方案和实施计划 Markdown。Tiny 使用独立 `adaptive-delivery-tiny` v1，`adaptive-delivery-plan` v2 的 documents 语义保持不变。

Tiny v1 同时固定 intent、non-goals、exact project-relative `changeScope`、至少一条 focused deterministic validation、`review=none` 和全部低风险否决声明。unknown field、空/重复/绝对/逃逸路径、缺失 validation 或任一风险声明不满足时 strict parse 失败。runtime 在 TUI approval 后自行捕获 workspace identity、HEAD、branch、clean Git status 和 approval digest baseline；模型不能自证 baseline。

### 9.1 技术方案

技术方案回答“为什么改、改成什么”，至少包含：

- 用户、场景、目标和当前问题
- 当前代码、配置、测试和运行事实
- 需求基线与可观察验收标准
- 明确不做的范围
- 业务规则、假设和待确认决策
- 架构、接口、数据和工作流变化
- 备选方案与取舍
- 兼容性、安全、成本和运行风险
- 验证策略与用户验收边界

### 9.2 实施计划

实施计划回答“如何落地和证明完成”，至少包含：

- 有依赖顺序的里程碑
- 每个里程碑的目标结果和影响契约
- 允许修改的模块或边界
- 必须增加或调整的测试
- 验证命令与完成条件
- 停止并询问用户的情况
- 对应项目事实源和唯一进度台账

实施计划不得引入技术方案中未确认的产品、范围或架构决策。

### 9.3 自适应详细程度

- Tiny：简短 intent/non-goals/scope/validation contract，一次 TUI 批准，不生成项目规划文档。
- Standard：先批准技术方案，再生成并批准实施计划。
- High-Risk：技术方案先经过 oracle 挑战，再执行两次独立批准。

Tiny 只省略 persistent 文档和独立 review 等仪式，不省略授权与 runtime safety。Standard/High-Risk 不允许先写代码后补方案。

### 9.4 面向用户的效果对齐

技术方案首先用大白话说明“做完以后会是什么样”，让用户先判断父会话是否真正理解需求，再阅读技术实现。方案面向用户的第一层固定包含：

- 当前要解决的问题，以及父会话对需求的简短复述。
- 用户完成任务后能够看到或操作到的最终效果。
- 正常、失败和关键边界场景下系统分别如何表现。
- 本次明确不做的内容，防止实现自行扩大范围。
- 可以直接判断完成与否的示例和验收结果。
- 仍需用户决定的产品、范围或风险选择。

架构、接口、状态、数据和代码细节放在第二层，并解释它们如何支撑前述效果，不用技术术语代替用户可观察结果。必要术语首次出现时使用大白话解释。

用户批准技术方案，表示批准上述最终效果、边界和验收标准。实施计划中的每个里程碑必须能对应到已批准效果或验收项；无法对应的工作不进入当前计划。开发期间若发现需要改变最终效果、非目标、范围、架构或验收标准，必须停止并调用 `/delivery-revise`，不能借实现细节、测试修复或 review 返工静默偏离原计划。

#### 9.4.1 内置方案追问模式

Package 在 `adaptive-delivery` Skill 内置“方案追问”，不依赖用户另行安装 `grilling` 或其他 Skill，也不新增运行时状态。该模式只帮助用户和父 Pi 在技术方案批准前关闭真正的决策歧义：

- 父 Pi 先读取代码、文档、配置、测试和项目规则；能够从项目事实确认的问题自行查证，不询问用户。
- 用户明确说“grill me”“把方案问透”“逐项对齐”时启用；否则仅在存在至少一个无法从事实确认、且会影响最终效果、范围、共享接口、数据、安全、费用或不可逆行为的决定时启用。
- 每次只问一个问题并等待回答；问题同时给出父 Pi 的推荐答案、推荐理由，以及不同选择会改变的用户可见结果。
- 推荐部分固定使用两行纯文本，第一行只写“推荐答案：”，第二行写具体推荐；不使用 Markdown 加粗标签，避免结束标记直接连接中文时被 TUI 原样显示。
- 用户可以用“按推荐”回答当前问题，不需要复述长篇内容。回答必须写回技术方案的业务规则、边界或验收标准，不能只留在对话摘要中。
- 所有高影响歧义关闭后立即停止追问并输出完整技术方案；实现偏好、命名、纯代码细节、未来扩展和可从仓库查明的事项不得延长问答。

极小需求默认零追问，但只有用户效果明确、无产品/架构决定、exact scope 可提前确定、修改局部可逆、workspace clean、无共享契约或外部副作用、无 dependency/toolchain 变化、无高风险领域且存在 focused deterministic validation 时才输出 Tiny contract 并走一次合并批准。auth/authorization/permission、tenant、secret、crypto、privacy、billing/payment/cost、migration/delete、事务/并发一致性、生产/部署/发布和不可逆外部写直接 High-Risk；风险优先于代码量。

方案追问负责向用户确认产品和范围决定；oracle 只在高风险方案中挑战技术取舍。两者不能互相替代，也不能在方案批准后继续静默改变已确认方向；批准后出现新决策仍使用 `/delivery-revise`。

#### 9.4.2 技术方案图表与 TUI 展示

技术方案在图表能够显著降低理解成本时使用标准 Mermaid 源码表达设计，不为装饰强制画图：

- 极小、单步骤且无状态/跨模块交互的需求不强制图表。
- 中大型任务存在多步骤流程、跨组件调用、状态变化、模块关系或数据流时，选择最有帮助的 1 至 3 张图。
- 高风险任务必须用适用图表画清关键路径、状态变化或信任边界；文字仍说明不变量、失败表现和恢复方式。
- Package 保证流程图、时序图、状态图、类图、ER 图和 XY 图六类；其他 Mermaid 类型保留源码并显示不支持说明，不引入浏览器运行时。
- 每张图只回答一个主要问题。复杂系统优先拆成“方案与批准”“实现与验证”“阻塞与恢复”等阶段图，不把完整生命周期、全部分支和异常路径压进同一画布。流程/状态图通常不超过约 10 个主要节点；时序图通常不超过 6 个参与者和 12 条主要消息，超出时按职责拆图。节点和连线使用短语而不是整段说明，并按结构选择横向或纵向布局，正文承载完整解释。

assistant 原始消息和需求级技术方案 Markdown 始终保存标准 `mermaid` fence，作为批准、恢复和跨工具可移植的事实。Delivery Gate 注册 display-only Markdown transformer，在 TUI 中把完整 fence 替换为简短占位；`message_end` 从未变换的 assistant 消息提取同一源码并暂存，等原始消息已经写入 Session 后再由 `agent_end` 追加不进入模型上下文的 TUI-only diagram entry。该 entry 不是批准主体，不参与 plan contract 或 candidate digest。

图表使用 `beautiful-mermaid` 在本地、无 DOM/浏览器条件下生成 SVG 和 Unicode 字符回退，再使用 `@resvg/resvg-js` 在内存中转为 PNG。PNG 默认按 3 倍像素密度栅格化，使用紧凑但不重叠的画布间距、几何精度提示和高对比度明暗配色；栅格尺寸仍限制在 2400×4800、编码结果限制在 2 MB。支持 Kitty、iTerm2、Ghostty、WezTerm 或 Warp 图片协议时，entry renderer 不再设置低于视口的固定宽度，交由 Pi `Image` 按当前终端可用宽度和原始纵横比布局；长图进入终端滚动区域，而不是为同屏展示整图缩小文字。为避免异常纵横比制造无界 transcript，单图仍保留 1000 行显示安全上限。不支持图片时显示字符图。渲染不调用 Provider、不访问网络、不执行 Mermaid 中的命令，也不写目标 Git 工作区。

渲染输入限制为完整 fence、六类已知 header、每条有界源码和每条 assistant 消息有界图数；初始化指令、控制字符、未知类型、解析失败或 PNG 超限时显示中文失败说明及原始源码，不伪造图片。图表只是文字方案的辅助视图：每张图前后必须有可读标题或说明，失败时技术方案仍可仅凭正文和 Mermaid 源码理解。

### 9.5 需求级规划文档

本节只适用于 Standard/High-Risk。Tiny 的 planning artifact 是 Session assistant entry、approval record、runtime state、approval baseline 和后续 candidate/evidence metadata，不创建需求级技术方案或实施计划 Markdown，也不注册 progress target。

当前项目已经存在总技术方案或总实施计划时，Package 默认把它们作为只读背景事实，不因文件存在就持续追加每个新需求。除非用户或项目规则明确要求复用现有文件，否则每个需求使用同一需求短名称创建一对独立文档：

```text
docs/<需求短名称>-技术方案.md
docs/<需求短名称>-实施计划.md
```

路径选择顺序为：当前用户明确要求、目标路径最近的项目 `AGENTS.md` 与文档路由、用户全局规则、Package 默认。用户要求与项目强制规则冲突、项目要求远程 Issue/TODO、存在多个唯一台账候选或无法证明路径职责时，必须停止询问，不能静默回退到默认路径。

需求短名称描述稳定的用户目标，不使用日期、`final-v2`、代码行号或可能变化的实现细节。计划回复必须显示需求短名称、两条 project-relative Markdown 路径和选择来源；新建文件的 basename 必须包含同一个需求短名称。路径一经批准不能静默改变。

技术方案和实施计划仍先在 Session 中形成并由用户批准。Standard/High-Risk 的 `/delivery-approve-solution` TUI 对话显示需求名和两条目标路径；首次确认后，Extension 获取短生命周期 canonical workspace lease，以 create-only、no-follow 方式立即写入技术方案，保存独立 `solutionDocument` 摘要证据后释放 lease，再进入 `PLANNING`，不得开放源码工具。`/delivery-approve-plan` 再次复验 approved solution entry、路径契约、方案文件 regular/symlink 边界和内容摘要，首次只 create-only 写入实施计划，并把两阶段证据合并为完整 `planningDocuments`。兼容的 plan-v2 combined 路径仍在一次批准后原子创建两份文件。已同步两份文档后执行 `/delivery-revise` 时，runtime 保留原 `planningDocuments` 作为覆盖前证据；重新批准只允许原地更新路径、文件身份和现场摘要仍与该证据一致的 Package 文档，任一外部修改或 symlink/父目录身份漂移都失败关闭，不能退化为任意覆盖。

任一目标已存在、位于 Git root 外、经过 symlink、不是 Markdown、内容标记不唯一或写入失败时保持只读并进入可恢复 `BLOCKED`。两份文件成功落盘并保存内容摘要后，才允许进入 `IMPLEMENTING`。Session message 及其摘要始终是授权主体；项目文档是长期记录，不能通过直接修改文件反向授予权限。

若需求、范围、架构或验收变化，`/delivery-revise` 清除相应 approval，但保留已冻结需求名、两条路径和现有文档 evidence。规划文档 evidence v2 持久化文件及各级父目录的 `dev/ino`、路径和内容摘要；plan 同时保留不可变的批准原文摘要与可由受控 progress sync 刷新的现场摘要，授权链校验前者，恢复和修订校验后者。旧 evidence v1 不隐式迁移，恢复时失败关闭并要求重新进入流程。新 solution/plan 必须继续使用同一文档契约；重新批准时 Extension 复验持久化身份与旧摘要，在目标同目录创建排他临时文件，完整写入并 `fsync`。rename 前必须先持久化 revision intent v1，其中同时绑定旧/新文件身份、父目录身份和摘要；该 checkpoint 必须保持修订前的 approvals、`planContract` 和 document evidence，不得提前混入新版批准语义。持久化后再次复验目标及关联文档，再以 rename 原子替换并同步父目录；只有文档替换成功后，最终 checkpoint 才一次性提交新版 approval、`planContract`、document evidence 并清除 intent。Session 恢复或同会话重试只接受磁盘精确匹配 intent 的完整旧态或完整新态：旧态清除 intent 并沿用旧 evidence，新态采纳新 evidence 后清除 intent，两种结果都回到未批准的方案或计划阶段并要求重新批准；其他现场继续失败关闭。solution 修订还必须确认旧 plan evidence 未漂移，避免留下半套新旧文档。人工改动、路径身份变化、symlink 或摘要不符一律拒绝覆盖；替换前失败时旧文件保持完整且清理临时文件。

项目已有唯一总台账时，父会话必须按项目规则把需求级实施计划登记为本任务唯一台账或停止询问；总台账只保留链接，不得与需求级计划重复维护状态。Package 不自动解析或重写总台账结构。

### 9.6 项目进度与运行时断点

Package 不规定统一 item ID、状态集合、Markdown 结构或转换规则，也不解析和改写项目计划。项目继续使用自身 `AGENTS.md` 和事实源指定的实施计划、Issue、TODO 或其他唯一进度台账。

Extension 只保存与恢复编排所需的运行时断点：当前交付阶段、已完成到的位置、active run、writer lease、candidate/evidence 引用、阻塞原因、恢复条件和下一步。断点在每次可证明的状态变化后立即写入 Session custom entry，不与项目文件组成跨存储事务。

父会话在以下 writer-free 边界，根据项目既有规则及时回写项目进度：

- child writer 已有可靠 terminal/process proof，且不再持有 workspace lease。
- 候选已经形成并准备验证。
- 一个独立事项已经通过要求的 gate/review。
- 流程进入 `BLOCKED`、`CANCELLED` 或准备进入 `DELIVERED`。

回写前父会话通过 Extension 固定的 `delivery_progress_sync` 入口为该次项目文档更新单独获取 workspace lease；Extension 只在该受限入口内修改批准的 exact progress target，完成后立即释放。若项目没有进度台账、当前项目规则不允许回写或 writer 状态不明确，则只保存运行时断点并在最终报告中标记“项目进度待同步”，不能为此启动第二个 writer。

任何进度回写若改变目标、范围、依赖或验收标准，都不再是普通进度更新，必须调用 `/delivery-revise` 并重新批准。

## 10. 交付状态机

```text
IDLE
  -> SHAPING
  -> SOLUTION_PENDING_APPROVAL
  -> PLANNING
  -> PLAN_PENDING_APPROVAL
  -> IMPLEMENTING
  -> VALIDATING
  -> REWORKING
  -> VALIDATING
  -> DELIVERED

任意活动状态 -> BLOCKED
BLOCKED -- /delivery-resume --> resumeState
任意非终态 -> CANCELLED

Tiny 与兼容的 plan-v2 combined 路径复用现有状态：
SHAPING -> COMBINED_PENDING_APPROVAL -> IMPLEMENTING
```

不新增 `TINY_PENDING_APPROVAL`。contract type、delivery profile 和 runtime metadata 足以区分 Tiny，避免状态机分叉。

### 10.1 状态标识与中文显示

状态持久化、Extension 内部判断、RPC 和结构化制品始终使用稳定英文枚举；面向用户的 TUI、`/delivery-status`、通知和文档使用中文主标签，并同时保留英文标识用于诊断。

| 内部状态 | 中文状态 | 推荐显示 |
|---|---|---|
| `IDLE` | 空闲 | `空闲 [IDLE]` |
| `SHAPING` | 方案梳理中 | `方案梳理中 [SHAPING]` |
| `SOLUTION_PENDING_APPROVAL` | 技术方案待确认 | `技术方案待确认 [SOLUTION_PENDING_APPROVAL]` |
| `PLANNING` | 实施计划编制中 | `实施计划编制中 [PLANNING]` |
| `PLAN_PENDING_APPROVAL` | 实施计划待确认 | `实施计划待确认 [PLAN_PENDING_APPROVAL]` |
| `COMBINED_PENDING_APPROVAL` | 方案与计划待合并确认 | `方案与计划待合并确认 [COMBINED_PENDING_APPROVAL]` |
| `IMPLEMENTING` | 开发中 | `开发中 [IMPLEMENTING]` |
| `VALIDATING` | 验证中 | `验证中 [VALIDATING]` |
| `REWORKING` | 返工中 | `返工中 [REWORKING]` |
| `BLOCKED` | 已阻塞 | `已阻塞 [BLOCKED]` |
| `DELIVERED` | 已交付 | `已交付 [DELIVERED]` |
| `CANCELLED` | 已取消 | `已取消 [CANCELLED]` |

中文标签只属于展示层，不作为状态机输入，也不写入需要机器解析的状态字段。后续调整中文文案不构成状态格式迁移。

除稳定英文状态枚举外，validation/review/evidence 状态、writer owner 类型、文档同步状态、checkpoint、`nextReadyAction`、阻塞原因和确认框字段也采用双层表达：Session custom state、tool 参数、协议和内部诊断继续保存英文；TUI 通过纯展示映射输出中文。路径、digest、run ID 和 `[STATE]` 可作为原样诊断值保留。旧 Session 中已经持久化的英文 checkpoint 在显示时即时翻译，不修改原始 entry。

### 10.2 状态转换规则

- `/delivery-shape` 开始只读侦察并进入 `SHAPING`。
- 用户批准技术方案后进入 `PLANNING`。
- 用户批准 Standard/High-Risk 实施计划，或批准 Tiny contract 且 runtime baseline 捕获成功后进入 `IMPLEMENTING`。
- worker 完成候选改动后进入 `VALIDATING`。
- 验证发现有效 P0/P1 后，父会话批准具体返工范围并进入 `REWORKING`。
- 返工候选产生任何变化后重新进入 `VALIDATING`，旧验证和审查证据失效。
- 所有必要门禁通过且无未处理 P0/P1 后进入 `DELIVERED`。
- 未授权决策、环境问题或验证失败进入 `BLOCKED`。
- 进入 `BLOCKED` 时保存来源状态 `resumeState`、阻塞原因和恢复条件。
- 用户解决阻塞后调用 `/delivery-resume`；Extension 重新校验批准、cwd、lease、候选和证据，成功后才返回 `resumeState`，否则保持 `BLOCKED`。`VALIDATING` 必须证明现场仍是冻结 candidate；`REWORKING` 允许批准范围内的部分返工改变现场，但返工前的 validation/review/Tiny evidence 仍必须绑定旧 candidate。恢复状态和策略提交成功后自动继续不需要新决策的 plan/run；待批准状态仍等待用户。
- 用户可以随时取消；取消不自动回退已有项目修改。
- 产品、范围或架构变化退回 `SHAPING`；仅实施顺序变化退回 `PLANNING`。

批准只绑定当前 Session 活动分支上的对应方案或计划条目。`/tree`、`/fork` 或方案重写后，旧批准不能自动覆盖新分支内容。

### 10.3 权限矩阵

| 状态 | 项目源文件写入 | 子 Agent | 宿主命令 | 说明 |
|---|---|---|---|---|
| `空闲 [IDLE]` | 禁止 | 禁止 | 禁止 | 尚未进入交付流程 |
| `方案梳理中 [SHAPING]` | 禁止 | 固定只读委派入口 | 禁止任意命令 | 只允许需求与代码侦察 |
| `技术方案待确认 [SOLUTION_PENDING_APPROVAL]` | 禁止 | 固定只读委派入口 | 禁止任意命令 | 等待用户批准不可变方案条目 |
| `实施计划编制中 [PLANNING]` | 禁止 | 固定只读委派入口 | 禁止任意命令 | 只生成实施计划 |
| `实施计划待确认 [PLAN_PENDING_APPROVAL]` | 禁止 | 固定只读委派入口 | 禁止任意命令 | 等待用户批准不可变计划条目 |
| `方案与计划待合并确认 [COMBINED_PENDING_APPROVAL]` | 禁止 | 固定只读委派入口 | 禁止任意命令 | Tiny 或兼容 plan-v2 的合并批准状态 |
| `开发中 [IMPLEMENTING]` | 仅 writer lease 持有者 | 一个写入者，可并行只读角色 | 仅批准范围 | 首次实现 |
| `验证中 [VALIDATING]` | 禁止 | Tiny 无 child；其他路径固定命令后才允许 fresh reviewer | 仅 contract 批准的验证命令 | 候选冻结并收集证据 |
| `返工中 [REWORKING]` | 仅 writer lease 持有者 | 原写入者 | 仅批准返工范围 | 只修复父会话接受的发现 |
| `已阻塞 [BLOCKED]` | 禁止 | 固定只读诊断入口 | 默认禁止 | 保存 resumeState，等待恢复条件 |
| `已交付 [DELIVERED]` | 禁止 | 禁止写入角色 | 禁止 | 交付后重新修改必须启动新流程 |
| `已取消 [CANCELLED]` | 禁止 | 禁止 | 禁止 | 不自动回退已有修改 |

Extension 使用一个串行化的 `applyPolicy()` 统一应用父工具策略、原始 `subagent` 策略、子 Agent capability ceiling 和 writer lease 状态。以下边界都必须调用它：

- 每次状态转换
- `session_start`
- `session_before_tree`，先收紧为只读再导航
- `session_tree`，按新活动分支恢复并重新应用
- Session 切换、fork、reload 和取消后的恢复路径

权限放宽只有在批准记录校验成功且 writer lease 可获取时才生效。任一策略应用、状态恢复或 lease 校验失败时，事务回退到只读策略；不得保留部分开放的写权限。`/tree` 不依赖 `session_start`，必须由 `session_tree` 显式恢复策略。

Pi hot reload 会把旧 Extension 退出时的 active tool 列表带给新实例。旧实例为安全而先收紧只读后，新实例不得把这份已收紧列表误认成用户原始工具配置。Extension 在同一 Pi 进程第一次加载时保存原始启用基线，reload 后复用该基线并只合并当前版本实际注册的 Delivery 工具；进程重启后重新从当次 Pi 配置采集。进入 writer 或 validation 状态时还要检查当前阶段的必需工具确实已被 Pi 激活，缺失时保持只读并进入可恢复 `BLOCKED`，不能显示写状态却没有对应工具。

Extension 的 Session checkpoint 不修改项目工作区。项目进度回写只能在无活跃 writer 且 lease 状态可证明时，由父会话临时取得 workspace lease 后按项目规则完成；该过程不开放独立的第二写入通道。

项目进度回写使用一个不改变基础交付状态的临时 `progress-sync` 控制面权限窗口。该窗口只允许项目规则明确指定的进度目标路径及其检查命令；不属于 `IMPLEMENTING`/`REWORKING` 的源文件实现权限，不能被 child writer 持有。

## 11. 开发编排

### 11.1 Tiny

```text
父 Pi exact-scope 实现
  -> focused runtime gate
  -> 交付
```

Tiny 必须同时满足全部 eligibility 条件，并使用 clean approval baseline。批准后 policy 将 `writablePaths` 投影为 exact scope，`edit/write` 调用前做 canonical path、Git root、symlink 和 exact membership 检查；candidate submit 前再次检查相对 baseline 的完整 Git delta。scope 外路径、staged、rename、delete、type change、symlink、submodule、HEAD/branch/workspace 漂移均失败关闭。Tiny 默认不使用 worker、reviewer、planning documents 或 progress sync。

为兼容既有 `adaptive-delivery-plan` v2，`small + low risk + low uncertainty` 的内部 `single` route 仍可由父 Pi 实现，但它属于 persistent plan 路径并保留 fresh reviewer，不等同于 Tiny。

### 11.2 中大型

```text
单 worker 实现当前里程碑
  -> runtime gate
  -> fresh reviewer
  -> 父会话分类发现
  -> 原 worker 修复有效 P0/P1
  -> 受影响门禁复验
  -> 更新唯一计划台账
```

### 11.3 高风险

```text
方案阶段 oracle 挑战
  -> 用户确认方向
  -> 单 worker 分里程碑实现
  -> runtime gate
  -> 正确性 / 测试 / 安全或契约多角度 reviewer
  -> 父会话裁决和返工
  -> 集成门禁与最终审查
```

高风险路径可以在第一次返工前使用多个互补角度的 reviewer 做同一波次集中发现，但不按固定轮数重复完整 review；返工和 closure review 服从下一节的收敛规则。

### 11.4 审查收敛与解题升级

review 的目标是关闭已确认风险，不是反复进行无边界探索直到“再也找不到问题”。中高风险任务在第一次返工前，对同一个冻结 candidate 完成一次集中发现：中风险通常使用一个完整 reviewer，高风险可以让不同角度的只读 reviewer 在同一波次并行检查，再由父会话一次性去重和裁决。

每个被父会话接受的 P0/P1 必须转成一个可验证关闭义务，至少记录：被破坏的不变量、最小复现或源码矛盾、修复后应成立的断言、受影响边界和关闭证据。该义务属于本次 review handoff 和 runtime checkpoint，不形成第二套 Issue 或计划系统。

原 writer 对全部 accepted P0/P1 做一次批量返工；返工期间以 regression/property test、固定 gate 或其他确定性证据判断问题是否关闭，不在每个局部修改后重新启动完整 review。返工候选形成后只做一次 closure review，范围限定为：

- 原 accepted P0/P1 是否已经关闭。
- 修复直接影响的调用链、状态、权限和异常路径。
- 修复是否直接引入新的 P0/P1 regression。

closure review 发现与本次修复无关的历史问题时，另行记录为新任务；P2、推测性意见和未来优化只进入最终 notes，不触发当前返工。同一最小复现仍失败，或同一不变量继续出现新的 P0/P1 变体，表示当前局部修复策略没有收敛，必须返回 `SHAPING` 或 `PLANNING` 重做相应机制并重新批准，不能继续堆叠补丁。

运行次数或资源预算只用于防止失控执行，不作为质量裁决：预算结束时仍有已证实、未关闭的 P0/P1 才进入 `BLOCKED`；全部 accepted P0/P1 已有关闭证据时进入 `DELIVERED`，P2 和已知验证缺口在最终报告中说明。

### 11.5 并行规则

- 只读侦察、研究和不同角度审查可以并行。
- 同一 cwd 不允许并行 writer。
- 只有任务真正独立、契约明确且 Git HEAD 干净时，才允许使用隔离 worktree 并行 writer。
- 依赖强、共享同一代码接缝或需要顺序反馈的任务保持串行。

### 12.1 Prompt Templates

- `/delivery-shape`：启动需求澄清、代码侦察和技术方案输出。
- `/delivery-plan`：在技术方案批准后输出实施计划。
- `/delivery-run`：在实施计划批准后启动自适应交付。

Prompt 只提供用户入口和当前阶段目标，不承载完整策略，避免三份模板重复维护规则。

待批准的技术方案和实施计划必须是当前 Session 活动分支中的不可变 assistant 消息条目，不接受 runtime artifact、可变文件或外部 URL 作为批准对象。方案生成期间不写目标项目；用户在 TUI 批准 solution 后，同一次明确授权只允许 Extension 同步技术方案。计划生成期间仍保持源码只读；批准 plan 后只同步实施计划。完整文档证据形成前不开放功能代码、配置或测试写入；写入后的文件也不能反向替代原始批准条目。

### 12.2 Skill

`adaptive-delivery` 是父会话的编排策略事实源，负责：

- 状态和产物定义
- 自适应判断原则
- 子 Agent 冷启动任务契约
- 单写入者和 worktree 规则
- acceptance、review、返工和停止条件
- 项目事实源、计划台账和最终报告边界

### 12.3 Delivery Gate Extension

Extension 只提供模型不能自行保证的运行时边界：

- 保存和恢复当前交付状态。
- 注册状态、批准、退回和取消命令。
- 未获实施批准前阻止父会话的内置 `edit`、`write` 和模型发起的任意 `bash`。
- 未获实施批准前阻止模型直接调用原始 `subagent`、`bg_wait` 和所有 subagent 管理动作。
- 提供一个参数受限的只读委派工具，并限制 child 为 native Pi read-only runner。
- 未获实施批准前限制子 Agent 为只读角色和只读工具。
- 方案或计划失效时立即恢复只读边界。
- 管理 canonical cwd/worktree writer lease 和候选摘要失效。
- 在 Session 中持久化运行时断点、证据引用和恢复条件。
- 在 TUI 以中文主标签和英文枚举显示当前阶段、待批准状态和阻塞状态。
- 从 assistant 原始 Markdown 提取有界 Mermaid，在不改变消息内容的前提下追加并渲染 TUI-only 图表 entry。

Extension 不判断方案是否优秀，不解析自然语言替用户批准，也不实现测试、计划或子 Agent runtime。

### 12.4 pi-subagents

`pi-subagents` 是本 Package 固定 bundled 的子 Agent runtime，继续负责：

- Agent 发现和角色配置
- fresh/fork context
- workflowScript、异步执行和 supervisor 通信
- Mission、Fleet、运行制品和恢复
- acceptance、worktree 和 Watchdog

Pi Package 之间使用独立 module root，不能把另一 Pi Package 当作普通 peer 共享。因此 manifest 先且只加载 bundled `pi-subagents` Extension，再加载 `delivery-gate`；两者从同一物理依赖目录使用 capability-ceiling、preflight 和 structured delegation 公开 API。用户不再单独安装 runtime owner。RPC ping 在执行前短暂收集响应：没有 owner 或检测到多个 owner 都失败关闭，不能启动 child、产生费用或假装门禁已生效。manifest 同时暴露 bundled `pi-subagents` 的 Skill 和 Prompt，确保移除独立 Package 后仍保留完整多 Agent 使用入口。Pi 会在项目过滤前预加载用户级 Extension 参与 project trust，因此项目过滤不能作为卸载已启动全局 owner 的安全证明；安装本 Package 前必须从同一 Pi 作用域移除独立 owner，或使用隔离 `PI_CODING_AGENT_DIR` 验证。

## 13. 审批与硬门禁

### 13.1 用户命令

目标命令面保持最小：

- `/delivery-status`
- `/delivery-approve-solution`
- `/delivery-approve-plan`
- `/delivery-revise`
- `/delivery-resume`
- `/delivery-force-release-lease`
- `/delivery-cancel`

所有可能放宽权限的动作，包括批准技术方案、批准实施计划、从 `BLOCKED` resume 和强制释放 writer lease，只能由交互式 TUI 中的用户操作触发，不注册为 LLM 可调用工具。模型可以建议用户执行，也可以主动使批准失效，但不能自行授予或恢复权限。

这些动作必须检查 `ctx.mode === "tui"`，并显示不可自动确认的用户对话，明确目标条目、恢复状态或 lease owner。print、JSON、RPC、Extension 注入消息和子 Agent 请求全部失败关闭；仅处于 TUI 模式但没有实际用户确认也不能放宽权限。未来若支持宿主系统授权，必须另行设计可验证的主体与请求关联协议。

批准或恢复后的非决策步骤自动继续并在 TUI 对话区可见：技术方案批准、方案文档同步、lease 释放和 `PLANNING` 状态持久化全部成功后，Extension 显示路径并自动发送展开后的 `/delivery-plan`；实施计划批准、计划文档同步且 `IMPLEMENTING` 状态持久化成功后，显示需求名、文档路径和下一步，并自动发送展开后的 `/delivery-run`。TUI 用户确认 `/delivery-resume` 且目标状态、必要 lease 与策略全部提交成功后，`PLANNING` 自动发送 `/delivery-plan`，`IMPLEMENTING`、`REWORKING`、`VALIDATING` 自动发送 `/delivery-run`；方案/计划待批准状态不得自动批准。自动发送本身不构成新的授权，只消费刚完成的 TUI 用户批准或恢复确认。

`/delivery-plan` 和 `/delivery-run` 继续保留为恢复与手工重试入口。自动发送失败时不得伪造“正在执行”或回退批准/恢复，只显示明确 warning 和应手工运行的命令；确认取消、非 TUI、文档同步失败、checkpoint 失败、lease 获取失败或策略应用失败时不得自动继续。底部状态只表达交付阶段，聊天区状态消息和随后出现的模型/tool 行才表达真实执行活动。

`adaptive-delivery-documents`、`adaptive-delivery-plan` 和 solution/plan marker 是内部解析协议，不属于用户界面或项目文档正文。Extension 使用 Pi display-only Markdown transformer 在 assistant 流式与最终渲染中隐藏这些块；Session 原始消息保持不变，approval digest、分支恢复和 plan 解析继续读取原始内容。planning-document writer 从标记正文中移除内部 fence 后再落盘，确保需求级文档只包含人类可读方案与计划。显示转换失败不得修改或伪造原始 Session 数据。

每个批准记录必须保存并校验：

- 批准类型：技术方案、实施计划或小型任务合并批准
- Session ID
- 被批准 assistant message 的 entry ID
- 被批准消息持久化内容的 SHA-256 摘要
- 批准时活动分支的 leaf/anchor entry ID
- canonical cwd 与 Git root（存在时）
- 需求短名称、技术方案路径、实施计划路径、路径选择来源和初始文档内容摘要
- 批准时间

批准时和每次恢复时都要证明目标 entry 存在于当前活动分支、内容摘要一致且 cwd 未变化。任一条件无法证明时，批准失效并回到只读状态。runtime artifact 只能作为辅助证据，不能成为授权主体。

Extension 额外注册模型可调用的 `delivery_invalidate` 工具。该工具只有降权能力，但三个 target 的语义不同：`SHAPING` 撤销全部批准，`PLANNING` 只保留有效 solution 批准，`BLOCKED` 表示临时停止，释放可证明属于父会话的 writer lease，同时保留批准链、规划文档契约、candidate 和已有 evidence，并记录原阶段为 `resumeState`。只有 TUI 用户执行 `/delivery-resume` 才能重新校验并恢复；模型不能把临时工具可见性问题变成破坏性撤销。

### 13.2 父会话工具边界

除 `IMPLEMENTING` 和已批准范围内的 `REWORKING` 外，父会话始终使用只读策略：

- 允许 `read`、`grep`、`find`、`ls` 等只读工具。
- 阻止模型调用 `edit`、`write` 和任意 `bash`。
- 阻止模型直接调用原始 `subagent`，包括 `gate`、`acceptance.verify`、workflowScript、worktree、output、resume、schedule 和管理动作。
- `VALIDATING` 中的宿主命令只能通过 Package 固定验证入口执行实施计划已批准的命令，并绑定当前 candidate digest；不能恢复原始 `bash` 或原始 `subagent`。
- 用户自己执行的 `!` / `!!` 命令仍属于用户操作，不作为模型授权来源。

只有进入 `IMPLEMENTING` 或已批准范围内的 `REWORKING`，且批准记录与 writer lease 校验成功后，`applyPolicy()` 才按当前写入者身份开放对应写工具。不得整体恢复进入流程前的工具集合；原始 `subagent` 在所有状态下始终受 Package 的状态策略、writer lease 和参数策略控制。项目 `AGENTS.md` 与用户授权继续作为更高层约束。

Delivery 工具按状态和 plan route 动态开放：`single` 的 `IMPLEMENTING`/`REWORKING` 向父 Pi 开放源码写入与 `delivery_submit_candidate`；`standard/high-risk` 只开放 `delivery_delegate_worker`，父 Pi 没有 `edit/write`。worker terminal 成功后 Extension 自动冻结 candidate；切换到 `VALIDATING` 后，下一次模型请求才开放 validate、review、rework 和 finalize。Extension 提供始终只读的 `delivery_runtime_status`，返回当前状态、实现方式、worker run、active tools、断点和下一步。

唯一的非 writer 写入例外是 §13.5 的临时 `progress-sync` 控制面窗口。该窗口不恢复原始工具集合，只为 exact canonical 进度目标开放路径受限的 `edit`/`write`，并通过 Extension 固定入口执行项目已声明的检查命令；原始 `bash` 和原始 `subagent` 继续关闭。

### 13.3 固定只读委派入口

审批前只开放 Package 自己注册的 `delivery_delegate_readonly` 工具。它的公开角色只有高风险 `oracle`，参数只包含任务文本和可选的只读关注点，不暴露以下能力：

- `gate` 或 `acceptance.verify`
- `output`、任意文件路径或 repo 写入
- worktree、resume、steer、schedule 或管理动作
- external CLI/job runner
- writer、delegate 或嵌套 subagent

该工具通过 bundled `pi-subagents` 的 structured delegation API 启动 foreground native Pi child。启动前使用同一物理 runtime 的 preflight 校验实际解析出的 Agent、runner、工具、Extension、MCP、cwd、capability ceiling 和输出绑定；readonly/validation ceiling 必须设置 `denyExtensions:true`，并由 capability audit 证明 ambient/configured Extensions 已禁用。pi-subagents foreground runtime 会注入 supervisor bridge，但该增强不在 public preflight 投影内，因此 Package 使用双证据：启动前后 public preflight 的安全契约必须一致；terminal response 必须携带真实 run ID、builtin agent、实际模型、thinking 和非空 runtime `launchContractDigest`，且模型属于 preflight candidate。任一身份、摘要、唯一 owner 或前后 public contract 无法证明时失败关闭。

实施计划批准对话出现前，同一个公开 preflight 还必须证明 builtin reviewer 至少解析出一个未被 registry、model scope 或 model-exclusion cache 排除的 candidate。该检查不启动 child、不调用 Provider，也不证明模型未来一定在线；它只阻止在必要的独立审查资源已经明确不可用时仍创建规划文档、获取 writer lease并进入实现。Provider、具体模型、fallback 和 pi-subagents exclusion TTL 继续由用户/项目配置，Package 不硬编码或自动改写。

调用者不能提供 `output`、`outputMode` 或任意路径。内置 Agent 自身可以声明默认 output，但 preflight 必须证明解析后的输出只落到 Session 或 temp runtime 托管目录，且 canonical 路径位于目标 Git root 外。输出位于项目目录、任意外部持久路径或无法证明边界时，委派失败关闭。只读结果可以由 runtime 保存为受控制品并通过工具返回引用，但不能形成目标仓库写入。

### 13.4 子 Agent 能力边界

Extension 在所有非 writer 状态使用 `pi-subagents` 的 session-scoped capability ceiling，并按状态收紧允许的角色和工具：

- `SHAPING`、方案/计划待批准和 `PLANNING` 的模型可调用只读委派只允许 builtin `oracle`；builtin reviewer 仅供 plan 预检使用。
- `VALIDATING` 只允许固定 validator/reviewer 入口和批准计划中的验证路径。
- `BLOCKED` 只允许固定只读诊断入口；`IDLE`、`DELIVERED` 和 `CANCELLED` 不允许子 Agent。
- 工具集合与当前状态明确允许的只读或验证工具上限取交集。
- readonly/validation 状态使用 `denyExtensions:true`，拒绝 ambient/configured Extensions、MCP 和 tool Extension path。
- 只允许 native Pi runner，拒绝 external CLI/job runner。
- 禁止 writer、外部 writer 和嵌套写入绕过父会话门禁。

该能力是同一进程内的策略边界，不是对恶意 Extension 或宿主进程的安全沙箱。Pi Extension 拥有当前用户权限；不受信任任务仍需容器、VM 或操作系统级隔离。

### 13.5 项目进度回写边界

Package 不注册项目计划改写工具，不解析项目 Markdown，也不定义统一进度状态机。项目进度由父会话在 writer-free 边界按当前项目规则更新：

- 确认没有活跃 writer，且上一 writer 的 terminal/process proof 可验证。
- 父会话为项目进度更新单独获取 canonical workspace lease。
- 取得 lease 后、写项目文件前记录当前基础状态和 `progress-sync` operation checkpoint；该初始 checkpoint 失败且 lease 释放与策略恢复都可证明时，清除内存 lease 并回到调用前状态，允许精确重试。
- `applyPolicy()` 临时只开放项目规则解析出的 exact canonical 进度目标路径；其他 `edit`/`write` 调用由 `tool_call` 路径校验阻止。
- 使用项目已有格式更新指定的计划、Issue 或 TODO；远程 Issue API 只有项目规则和任务授权明确允许时才开放对应固定入口。
- 通过 Extension 固定检查入口运行项目已声明的文档或结构命令；不开放任意 Bash，记录 changed files 和 evidence 引用。
- 无论成功、失败或取消，都先恢复原基础状态的工具与 subagent 策略，再释放 lease。
- 把本次同步结果写入 Session checkpoint。

项目进度回写与 Session checkpoint 不组成原子双写。Session checkpoint 是运行时恢复事实，项目台账是项目进度事实；写入开始后的任一步失败都必须恢复只读策略并记录为 `BLOCKED` 或“项目进度待同步”，不得自动选择一方覆盖另一方。项目写入前的初始 checkpoint 失败不产生项目变更；若 lease 释放与策略恢复都可证明，可保留原状态供同一调用重试。若策略恢复或 lease 释放失败则保留 lease 并失败关闭。恢复时只做只读比较，并由项目规则或用户决定如何协调。

## 14. 状态、事实源与恢复

### 14.1 Session 状态

Extension 使用 Pi `custom` session entry 保存状态。状态至少包含：

- 当前阶段
- 任务标识和简短目标
- 风险与复杂度分类
- 已批准方案和计划的完整批准记录
- 项目进度台账引用或 canonical 路径（如有）
- 最后可证明断点、changed files 和 `nextReadyAction`
- 当前 Mission ID（如有）
- 当前 writer lease 标识（如有）
- 当前实现方式、worker run ID/status 与启动契约摘要（如有）
- 已批准的需求短名称、规划文档提案和 planning-document sync 证据
- 当前 candidate digest（如有）
- 当前 gate/review evidence 引用
- `resumeState`、阻塞原因和恢复条件（如有）
- 最近一次项目进度同步结果

`custom` entry 不进入模型上下文；Extension 在 `session_start` 和 `session_tree` 时从当前活动分支恢复最新状态，重新校验批准记录、writer lease、候选摘要和 evidence 引用，并通过隐藏或可见的阶段消息向模型提供必要上下文。恢复期间始终先应用只读策略，只有全部校验成功后才允许按状态放宽权限。

### 14.2 Writer Lease

单写入者从流程约定提升为 Package 保证范围内的 canonical workspace lease：

- lease key 使用 canonical Git worktree root；同一 worktree 的根目录与任意子目录共享一个 key，canonical cwd 只作为批准属性。
- 父会话直接实现和 foreground child worker 使用同一套 lease，不得各自维护独立标志。
- `single` 路径由父进程持有 lease并开放父 `edit/write`；`standard/high-risk` 由父进程作为 foreground lease custodian，但父工具策略只开放 `delivery_delegate_worker`，不开放父 `edit/write` 或 `delivery_submit_candidate`。
- foreground worker 运行在同一个阻塞工具调用内：tool-batch barrier 拒绝 sibling write，父会话在 terminal 前不能产生下一模型回合；其他受控 Pi 进程仍被同一 workspace lease 阻塞。
- worker 启动前 preflight 必须证明 builtin identity、fresh context、固定读写工具、无 fanout/ambient Extension/MCP、runtime-managed output 和可用模型；terminal response 的 run ID 与 `launchContractDigest` 必须匹配。
- worker 继续不获得通用 shell、ambient Extension 或 MCP。plan v2 的 validation item 可以显式批准一条可选确定性 `repairCommand` 及独立 timeout；Delivery Gate 只在唯一 worker 已取得可信 terminal、执行前重新证明 lease 仍由父进程保管且 candidate 尚未冻结的窗口顺序执行这些命令。调用者不能临时传入或改写命令；lease 无法重新证明时不执行 repair，任一修复命令失败都释放可证明 lease、保持只读并阻塞，不形成 candidate 或验证证据。纯展示回调异常不得改变 repair 的执行、阻塞或 lease 清理语义。
- worker terminal 成功后，Extension 在 child 已结束且 lease 仍由父进程保管时冻结 candidate，再释放 lease并进入 `VALIDATING`。失败 terminal proof 完整时释放 lease并进入可恢复 `BLOCKED`；proof 不完整时保留 lease。
- worktree writer 的 lease 只覆盖其 canonical worktree，不错误阻塞明确独立的其他 worktree。
- 当前版本不启动 async current-worktree worker。公开 API 在 child 启动前不提供可原子绑定的真实 run ID；不得采用“先启动、后 bind”的竞态方案。未来 async 路径必须先获得公开的 pre-launch claim/bind 能力，并在 package-owned terminal result 与 process-terminal proof 后释放。
- 进程状态、run 身份或清理证据不明确时保留 lease 并进入 `BLOCKED`，不得按超时推断 writer 已退出。
- acquire、bind、release 和 force-release 使用同一跨进程 operation lock；force-release 必须按用户确认时看到的 leaseId 条件删除，owner 已替换时拒绝。
- 手动恢复或强制释放必须由用户在 TUI 中确认，并显示 workspace、owner 和残余风险。

lease 存放在 Pi 用户状态目录而不是目标仓库，采用跨进程原子文件操作和 owner 校验。该保证只覆盖加载兼容 Package 的 Pi 会话及其受控 child；不能阻止外部编辑器、其他未加载 Package 的 Pi 进程或任意宿主进程写入。因此交付验证仍需使用 candidate digest 检测外部变化。

### 14.3 项目事实源

- Session 状态记录批准和恢复，不替代项目文档。
- Mission 记录子 Agent 执行、运行 ID、制品和恢复线索，不替代项目实施计划。
- 项目技术文档记录当前稳定设计。
- 项目自己的计划、Issue 或 TODO 按项目规则记录进度；Package 不规定其格式和状态。
- scratch review 和运行日志默认保存在 Session 或临时制品目录，不污染项目仓库。

Session checkpoint 是运行时恢复事实，项目计划/Issue/TODO 是项目进度事实，二者没有共同事务，也不互相覆盖。发现二者冲突时进入 `BLOCKED`，记录差异并交由项目规则或用户决定；Extension 不自动合并、回填或选择“更新”的一方。

### 14.4 Compaction 与分支

- Compaction 是有损摘要，但完整 Session JSONL 仍保留原始条目。
- 批准绑定 Session entry ID、内容摘要、活动分支锚点和 cwd，不绑定摘要中的自然语言重述。
- `/tree` 或 `/fork` 后按活动分支恢复状态；无法证明批准适用于新分支时降级为待批准，而不是沿用旧授权。

### 14.5 断线与恢复

Session 重开、Pi 重启、compaction 或父会话断线后，Extension 按以下顺序恢复：

1. 先应用全局只读策略，不根据上次内存状态开放权限。
2. 从当前活动分支读取最新 Delivery custom entry，并校验方案、计划和 cwd 批准记录。
3. 读取最后可证明断点、项目进度引用和最近一次同步结果；只读比较项目台账，不自动协调差异。
4. 使用 Mission、subagent terminal、process-terminal proof 和 writer lease 交叉确认正在运行或已终止的 child；固定验证不启动 child。
5. 重新计算 candidate digest，判断既有 gate/review evidence 是否仍有效。
6. 生成一个明确的 `nextReadyAction`，经 `applyPolicy()` 成功后才恢复对应入口。

恢复行为由 Extension checkpoint 的阶段、run 和 evidence 决定，不解析项目计划状态：

- `resumeState=VALIDATING`：不重复实现，重新计算候选并继续缺失或失效的固定验证/review。
- `resumeState=IMPLEMENTING/REWORKING` 且 foreground worker terminal proof 不完整：保留 custodian lease，不启动替代 worker。
- `resumeState=IMPLEMENTING/REWORKING` 且 worker 已有匹配 terminal proof：失败路径释放 lease并允许 TUI 恢复；`single` 回到父 writer，`standard/high-risk` 启动一个新的受控 foreground worker。本版本不假装续接已经终止的 OS 进程。
- writer 进程状态未知：保留 lease并保持 `BLOCKED`，不得按超时推断终止。
- 项目进度与 Session checkpoint 冲突：保持 `BLOCKED`，显示差异和所需决定。
- 其他只读阶段：返回保存的 `resumeState`，继续相应方案、计划或审批动作。

临时 `BLOCKED` 不清空授权事实。固定验证在一个前台工具调用内执行；每个命令服从批准 timeout 和用户中断信号。若 Session 恢复时最后 checkpoint 仍为 pending，Extension 无法证明旧宿主命令的终态，必须保持只读并标记 infrastructure failure；用户确认没有遗留命令后再恢复和重跑整个固定验证批次，不能把未知结果当成通过。

恢复不得重放结果未知的写入工具或宿主命令。`/delivery-status` 必须使用中文主标签和英文枚举显示当前状态，并列出 `resumeState`、最后断点、writer owner、证据有效性、项目进度同步状态和下一步，使用户能够判断恢复位置。

## 15. 模型与推理等级

Package 定义角色能力层级，不硬编码具体模型：

| 角色 | 建议能力层级 | 建议推理等级 |
|---|---|---|
| 中央架构师 `[父 Pi 会话]` | 强推理、意图与架构能力 | `high` / `max` |
| 代码侦察员 `[scout]` | bundled runtime 通用角色，当前 Delivery 流程不调用 | `low` |
| 开发执行者 `[worker]` | 可靠实现和多文件修改 | `high` / `max` |
| 独立审查员 `[reviewer]` | 强审查，尽量与 worker 互补 | `high` |
| 架构顾问 `[oracle]` | 顶级但有界的只读推理 | `high` / `max` |

具体 Provider、模型、fallback 和成本策略由用户级 `subagents.agentOverrides` 或 profile 配置。项目 Package 不要求用户拥有某个特定 Provider。

## 16. 验证与交付

### 16.1 验证来源

父会话从当前项目的 `AGENTS.md`、README、测试配置和相关事实源选择验证命令。Package 不维护跨语言命令别名表或通用测试猜测器。

固定验证不启动 AI child，也不依赖 reviewer 模型。Extension 从已经通过批准链整体校验的 Tiny v1 或 plan v2 contract 读取命令，并通过 Pi 公开 `pi.exec` 逐条执行；模型调用者不能传入、替换、追加命令或 timeout。长命令执行时，Delivery Gate 使用自有低频进度更新并在 TUI 临时隐藏 Pi 默认高频 working spinner，终态后恢复；显示失败不得改变命令执行和 evidence。`pi-subagents` 继续只负责高风险 oracle、唯一 worker 和 Standard/High-Risk 验证后的 fresh reviewer。

`delivery_validate` 保持当前工具调用，按顺序显示当前命令 ID、已完成命令、退出码和耗时。父模型只调用一次，不得通过重复调用 `delivery_runtime_status` 充当轮询器。完整 stdout/stderr 只保留有界工具结果；Session runtime state 保存批次 ID、candidate digest 和逐命令终态摘要，不复制完整日志。

命令启动失败或用户中断属于 infrastructure failure；非零退出或 timeout 只证明批准命令未通过。每个终态都先重新计算 candidate，候选变化时整批证据失效。全部命令通过并成功保存 terminal checkpoint 后，Tiny 可直接 finalize；Standard/High-Risk 才允许进入 fresh review。

此前的 async `reviewer + acceptance.verify` 方案已被真实项目否决：reviewer 在宿主命令运行前被要求报告命令结果，且 pi-subagents `0.62.0` 的公开 completion/status 投影不能稳定提供完整 terminal ledger。Package 不读取 pi-subagents 内部 artifact 路径或导入内部模块，因此改用上述 Pi 公开命令 API，而不是增加私有兼容层。

### 16.2 Candidate Digest

进入 `VALIDATING` 时，Extension 冻结一个逻辑候选并计算 `candidateDigest`。候选清单使用稳定 canonical JSON 表示，至少包含：

- canonical cwd、Git root 和 worktree identity
- 当前 HEAD commit；无 commit 时记录 unborn 状态
- index/staged diff 的内容摘要
- tracked worktree diff 的内容摘要
- 已批准任务范围内相关 untracked 文件的排序路径、Git mode 与内容摘要
- submodule 或其他项目明确要求纳入的工作区状态
- 对应技术方案、实施计划和返工批准记录摘要
- 已同步需求级技术方案文档的路径和当前内容

项目规则指定的进度计划、Issue 或 TODO 投影不用于授予权限，也不持久化为第二套 Extension digest。需求级技术方案是普通 candidate 文件；需求级实施计划同时是唯一进度制品，并作为显式 control-plane exclusion。control-plane exclusion 只接受 Git root 内现存 regular file：逐级拒绝 symlink component、拒绝目录，并保持批准的 lexical path，不对 realpath 目标执行排除。交付前现场计算项目进度制品的当前内容摘要，并与 candidate evidence 一起检查。进度内容与已批准计划契约冲突时进入 `BLOCKED`。

candidate v3 只表示 Git 可交付、可验证且可交给 reviewer 读取的变更。Git ignored 路径不进入 manifest、digest 或 reviewer packet；验证期间新增、修改或删除 cache、coverage、编译产物等 ignored artifact 不使 evidence 失效。任务若确实需要交付 ignored 文件，必须先调整 Git 管理方式，使其成为 tracked 或非 ignored untracked 内容，否则 Package 不得宣称该文件已验证或审查。非 ignored 的大文件和二进制 untracked 内容仍进入 candidate 内容摘要，并以有界语义进入 reviewer packet。无法稳定枚举相关 Git 可见内容时，候选进入 `BLOCKED`。

证据绑定规则：

- runtime gate 记录命令、有效环境、退出状态和 `candidateDigest`。
- validation runner 只迭代批准 plan contract 的原始命令数组；调用者参数为空。terminal checkpoint 必须绑定当前 candidate、批次 ID、全部批准命令 ID、状态、退出码和耗时；缺失、顺序不匹配、状态未知或 checkpoint 保存失败均失败关闭。最终交付再次核对全部命令为 `passed`。
- 批准验证命令失败只能证明“当前 candidate 在批准环境下未通过该命令”，不自动证明源码缺陷。父会话必须结合权威输出区分候选代码、验证环境和已批准计划错误；后两者不得借代码返工静默修改，计划错误使用 `/delivery-revise` 重新批准。
- Standard/High-Risk reviewer 启动前由 runtime 生成有界 canonical packet：staged diff、tracked worktree diff、带实际 Git mode 的 untracked text patch，以及 binary/large 的 mode、size、摘要和 symlink 的 JSON 转义 target。packet 同时记录 `candidateDigest`、`diffDigest` 和 changed paths；超过 192 KiB 时失败关闭而不是截断成不完整审查输入。untracked mode 同时进入 candidate manifest，review 期间的 `chmod` 会使旧 evidence 失效。
- reviewer 结果必须是严格 `adaptive-delivery-review` v1，回显同一 `candidateDigest` 和 `diffDigest`，并提供结构化 P0/P1/P2 findings 与一致 verdict；bare `Merge verdict: OK` 不形成证据。启动前、packet 生成后和返回后都重新计算候选，中途变化使结果失效。
- 任何代码、测试、配置、相关 untracked 或批准记录变化都会使既有 verified/reviewed evidence 失效。
- review 后修复必须进入 `REWORKING`，产生新 `candidateDigest`，并重新执行受影响验证。
- 项目进度回写完成后重新计算 candidate，确认除显式进度制品外的候选没有变化。
- 最终交付前现场读取项目进度制品并计算摘要，连同 `candidateDigest` 和有效 evidence 一起进入最终检查；不额外持久化第二套进度摘要。

candidate digest 和项目进度现场摘要是一致性证据，不是代码正确性证明，也不阻止外部进程写入。

### 16.3 Evidence 分级

- claimed：子 Agent 文字声称执行过验证。
- checked：runtime 检查了结构化证据和工作区状态。
- verified：runtime 实际执行批准的命令并成功。
- reviewed：fresh reviewer 已检查当前候选且无阻塞发现。

开发交付不能仅依赖 claimed evidence。

### 16.4 交付标准

- 已确认范围全部实现。
- 适用 runtime gates 通过。
- fresh review 没有未处理 P0/P1。
- runtime gates、review 和最终工作区绑定当前 candidate digest。
- 项目进度制品在交付前现场读取并计算摘要，其内容与已批准计划及验证证据一致。
- 最终 diff 只包含本任务范围。
- 项目事实源和唯一计划台账按项目规则更新。
- 未执行项、环境差异和残余风险明确。
- 浏览器、视觉或真实环境验收只有实际执行后才标记完成。
- commit、push、PR、npm 发布和部署状态明确，并默认未执行。

## 17. 安全与信任边界

- Pi Package 和 Extension 以当前用户权限执行，安装前必须审查来源。
- 项目级资源只有在 Pi project trust 通过后加载；trust 不是沙箱。
- Package 不读取或记录凭证、真实密钥、生产 `.env` 和敏感会话正文。
- 默认不出网、不上传指标、不分享 Session。
- researcher 出网、真实 Provider 调用、费用和生产操作继续由任务授权控制。
- 对不可信仓库或无人值守任务，必须使用容器、VM、微型虚拟机或等价系统隔离。
- 硬门禁只能约束声明支持的 Pi 工具和兼容子 Agent runtime，不能约束恶意同进程 Extension。

## 18. 人工驱动的持续优化

本 Package 不包含自动训练和自主自修改。持续优化采用人工控制的软件版本迭代：

```text
真实任务证据
  -> 人工分类失败
  -> 修改提案
  -> 固定评测集对比
  -> 人工批准
  -> 发布新版本
  -> 保留回滚
```

可在本地收集的最小指标包括：

- 任务分类和实际执行路径
- 首轮门禁结果
- reviewer P0/P1 数量、有效发现和误报
- 修复轮数、用户返工和逃逸缺陷
- 耗时、Token、成本、中断和恢复次数

指标默认只保存在本地，不包含源码、完整 Prompt、凭证或用户数据。任何 Prompt、Skill、角色配置或 Extension 变更都必须进入普通代码评审和版本发布流程。

## 19. 兼容性与分发

- 初期通过私有 Git 仓库安装和验证。
- 稳定后可发布 npm，并使用语义化版本。
- Package 使用 `package.json` 的 `pi` manifest 声明 Prompt、Skill 和 Extension。
- `pi-subagents` 同时提供库 API 和 runtime owner，但只允许来自本 Package 的同一份 bundled `0.64.0`：
  - `dependencies` 和 `bundledDependencies` 固定版本，manifest 加载其 Extension 入口并暴露同版本 Prompt 与 Skill。
  - 用户无需也不得再单独启用另一份 `pi-subagents` Extension；零 owner 或多 owner 在 child 启动前失败。
  - capability-ceiling、preflight、delegation 和实际 execution 使用同一物理 module root，避免 Extension 路径进入摘要后产生跨副本漂移。
  - RPC envelope 的 `version` 仍只是协议版本；依赖升级只能随本 Package 版本显式发生，并重新执行兼容矩阵和真实 TUI canary。
- 用户模型配置保留在 `~/.pi/agent/settings.json`，不随 Package 发布。
- 项目特有规则、命令和事实源不进入通用 Package。
- 升级不得静默改变审批语义；涉及状态格式或门禁行为的变更必须提供明确版本说明和回滚方式。
- `adaptive-delivery-plan` 当前版本为 v2。独立的规划文档同步 evidence 当前版本为 v2，v1 未持久化文件及父目录身份，严格恢复时失败关闭并要求重新进入流程，不提供隐式迁移。

## 20. 已知取舍与失败模式

| 风险 | 设计处理 |
|---|---|
| 小任务流程过重 | Tiny 使用 Session/runtime contract、一次批准、无需求级规划文档/worker/reviewer/progress sync |
| 用户确认疲劳 | Tiny 保留一次 TUI 授权；本版本不实现 auto-approve |
| 架构师形成单点偏差 | 高风险方案增加 oracle，最终仍由用户和父会话裁决 |
| 多 Agent 协调成本超过收益 | 顺序任务保持单 writer，只有独立读任务并行 |
| reviewer 与 worker 盲点相关 | fresh context、runtime 提供 actual diff、结果回绑 candidate/diff digest、不同审查角度和可选互补模型 |
| Agent 生成错误测试 oracle | 可信项目测试和 runtime gate 优先 |
| review/fix 不收敛 | 首轮集中发现、accepted P0/P1 转为可验证关闭义务、批量返工后只做 closure review；同一不变量再次失败时升级设计，不继续堆补丁 |
| Session 摘要或分支漂移导致批准错配 | 批准绑定 entry ID、内容摘要、分支锚点和 cwd，无法证明时降级为待批准 |
| 审批前通过 gate、acceptance 或 output 产生宿主写入 | 禁止原始 subagent，只开放无这些参数的固定只读委派入口 |
| Bash 或子 Agent 绕过写入门禁 | 父工具拦截、preflight 与子 Agent capability ceiling 同时生效 |
| 父会话和多个 worker 同时写 | canonical workspace writer lease，未知进程状态时保留 lease 并阻塞 |
| 只读状态无法合法回写项目进度 | writer-free 边界临时启用 path/command 受限的 progress-sync 控制面窗口，结束后恢复原策略 |
| resume 或强制释放被非用户来源触发 | 所有权限放宽动作要求交互式 TUI 用户确认；RPC、注入消息和 child 请求失败关闭 |
| 旧测试或 review 证明了旧候选 | 所有 gate/review 绑定 candidate digest；交付前现场检查项目进度制品及其当前摘要 |
| 断线后从头重跑或猜测完成 | 状态边界持久化 Session checkpoint，结合 Mission、lease 和 process proof 从最后可证明断点恢复 |
| public preflight 与 runtime 增强投影不同 | manifest 只加载 bundled owner；public preflight 启动前后保持一致，terminal 另行校验真实 run ID、agent、model、thinking 和 runtime digest |
| 单个 reviewer 模型瞬时失败 | 固定命令验证不依赖模型；plan 批准前仍为后续 fresh review 预检至少一个 candidate，用户可配置 fallback，pi-subagents exclusion TTL 属于独立 runtime 配置 |
| Mission 成为第二进度台账 | Mission 仅用于执行恢复，项目计划仍是事实源 |
| 自动优化放大错误 | 禁止自主生效，必须固定评测、人工批准和版本回滚 |

### 20.1 R22 真实 TUI canary 问题与 R23 修复决策

亚马逊目标项目两轮真实 TUI canary 已确认以下四类问题。前三项已有确定复现与代码归因；第四项目前只有 TTY 高频输出、读取延迟和命令超时的时间相关性，因此修复目标限定为消除 Package 可控的高频输出并复验，不把 Docker 或 Pi TUI 猜测成已证实根因。

| 问题 | 已确认事实 | R23 最小修复 | 验收标准 |
|---|---|---|---|
| 已落盘计划阻断同路径修订 | `/delivery-revise` 清除了完整文档证据；方案同步又无条件要求 plan path 不存在，后续 plan 仍只有 create-only 路径 | 修订时保留原完整文档 evidence；方案和计划分别只覆盖与旧摘要、路径和文件身份仍匹配的 Package 版本 | 已完成规划的 `BLOCKED` 会话可回到 `SHAPING` 或 `PLANNING` 并原路径重新批准；人工改动、symlink 或路径变化仍拒绝覆盖 |
| worker 无法确定性执行 formatter | builtin worker 的固定 allowlist 没有 shell，Black 精确改写只能靠模型猜测 | 保持 worker 无 shell；plan v2 validation item 增加可选、用户批准的 `repairCommand`/timeout，由 Delivery Gate 在 worker terminal 后、candidate freeze 前通过 `pi.exec` 顺序执行 | formatter 可在 lease 内确定性改写候选；未批准命令不能执行；失败时无 candidate/evidence 且权限失败关闭 |
| validation 失败后重复调用 `delivery_begin` | `delivery_begin` 在所有状态保持可见，Extension 虽拒绝非法调用，但模型连续四次选错工具 | `delivery_begin` 只在 `IDLE` 可见；其他状态保留 `delivery_runtime_status` 和当前阶段合法恢复工具 | `VALIDATING`、`BLOCKED`、`REWORKING` 等状态的 active tools 不含 `delivery_begin`，`IDLE` 仍可由真实 `/delivery-shape` 启动 |
| 长验证期间 TTY 高频重绘 | canary 捕获到数十万 token ANSI spinner，并与复验超时同时发生；根因归属未证明 | 使用 Pi 公开 TUI API 在 validation 命令窗口隐藏默认 working spinner；Package heartbeat 从 2 秒降为 30 秒，保留起始、低频运行和终态更新 | 自动化证明 UI 控制在成功、失败和异常路径恢复；新 canary 的终端输出显著收敛，再比较相同命令耗时，不预先宣称超时根因已修复 |

### 20.7 R29 第七轮 Canary 收口决策

第七轮亚马逊真实 TUI canary 证明 Standard worker 能完成实际模块拆分，但也暴露了三个 Package 控制面问题。首先，worker task 允许在计划显式授权时修改 progress target，而这些控制面文件又被 candidate 排除；因此 worker 对实施计划的修改没有在 terminal 后立即被 candidate freeze 捕获，只在下一轮规划文档授权复验时触发阻塞。其次，首次 `BLOCKED` 已保存 `resumeState=VALIDATING`，后续 provider 请求再次调用 runtime proof failure 时却以当前 `BLOCKED` 重新计算恢复点，导致原恢复状态丢失。最后，Package 已从公开委派更新事件获得当前工具、最近输出、耗时和工具数，但只把当前工具写入折叠的工具更新，没有进入持续状态栏和 `/delivery-status`。

R29 将 solution、plan 和 plan v2 的全部 `progressTargets` 定义为 worker 受保护制品。worker task 必须无条件禁止修改这些路径，即使批准计划把它们列为最终交付范围；项目进度仍只由父会话在 writer-free 的 validation/review 后通过 `delivery_progress_sync` 更新。公开 `pi-subagents` structured delegation 只提供工具名 capability ceiling，没有 child 路径过滤回调，因此 Package 不宣称能在操作系统层拦截 worker 的每次写入。本轮在委派前冻结受保护制品；worker terminal 后、repair 前执行第一次复验，批准 repair 完成后、candidate freeze 前再执行一次。快照读取自身也要求摘要前后的文件身份一致。任一复验发现内容、类型或身份漂移时都不形成候选，释放可证明 lease 并进入只读 `BLOCKED`；若原阶段为 `REWORKING`，继续保留与旧 candidate 绑定的 validation/review evidence，使受保护文档恢复后能够回到同一返工断点。

重复 runtime proof failure 若发生在已有 `BLOCKED` 状态，必须沿用已经持久化的 `resumeState`，不能用 `BLOCKED` 覆盖它；该规则同时适用于 provider/agent 边界、工具执行时授权复验、只读策略提交或 invalidate 失败、策略恢复和 checkpoint 写入失败。canonical lease 释放或归属复验无法证明时，运行时必须立即令缓存的 `leaseValid=false`，状态接口不得把保留的 lease reference 显示为仍持有。repair 前的归属复验无论返回失效还是直接抛出读取/解析异常，都必须保存可信 worker terminal 信息、以原实施阶段进入只读 `BLOCKED`，且不得执行 repair 或形成 candidate。worker 进度仅保存在当前 Extension 实例的有界瞬时内存中，不参与批准、lease、candidate 或恢复；状态栏显示净化后的当前工具、实时经过时间和工具数，`/delivery-status` 额外显示最近工具及一条有界输出。update 事件未携带工具名或 terminal response 已到达时都必须清除“当前工具”，不能把历史工具显示为仍在执行；最近工具继续保留供状态查询。Session reload 后没有真实 child 观察连接时不伪造实时进度，继续按未知 terminal proof 的既有规则阻塞。

R29 返工后的最终门禁为 typecheck、127/127 unit、99/99 integration、9/9 real Pi RPC E2E、pack、offline audit 和 `git diff --check` 全部通过。三轮可执行的限定只读 review 共发现四个 P1 和五个 P2，均完成最小返工；最终同一 reviewer 复核无剩余 finding，merge verdict 为 `OK`。该结论证明当前 Package diff 的自动化与审查闭环，不替代使用修复后 Package 恢复亚马逊 canary 现场并完成 validation/review/progress sync 的真实 TUI 证据。

## 21. 研究与经验依据

- [AgentCoder](https://arxiv.org/html/2312.13010v2) 表明程序员、测试设计和执行反馈分离可提升函数级代码生成，但其结论不覆盖真实仓库级开发。
- [Towards a Science of Scaling Agent Systems](https://arxiv.org/html/2512.08296v3) 表明多 Agent 效果依赖任务可分解性；中央协调优于无监督独立聚合，而顺序依赖强的仓库任务可能因多 Agent 增加成本和错误传播。该论文中的 SWE-bench Verified 子集里，多 Agent 架构平均略逊于单 Agent，且样本量有限。

这些研究只支持“按任务结构选择架构”，不证明多 Agent 普遍优于强单 Agent。因此本方案采用固定中央编排、按风险自适应 Agent 数量、确定性验证优先，而不把“更多 Agent”当作质量保证。

## 22. 方案验收标准

用户确认本技术方案时，视为确认以下目标设计：

1. 所有修改型任务都必须有 runtime 可解析并绑定当前 Session/workspace 的 Delivery Contract；planning artifact 不等于 persistent project documentation。
2. Tiny 使用独立 v1 contract、一次 TUI 批准且不创建需求级规划文档；Standard/High-Risk 保持 plan v2 和 persistent docs。
3. 最终 Package 包含 Prompt、Skill 和窄职责 Delivery Gate Extension。
4. Package 复用并要求兼容的 `pi-subagents`，不自行实现子 Agent runtime。
5. 未获实施批准前，禁止原始 subagent，只允许固定 native read-only delegation 入口。
6. 只有 `IMPLEMENTING` 和批准范围内的 `REWORKING` 可以持有源文件写权限；其他状态默认只读。
7. 批准对象绑定不可变 Session entry、内容摘要、活动分支和 cwd，并提供只降权的失效工具。
8. Package 使用 canonical workspace writer lease 保证受控流程内单写入者。
9. runtime gates 和最终工作区绑定 candidate digest；Standard/High-Risk review 额外绑定 runtime actual diff digest；交付前现场检查适用的项目进度制品及其当前摘要，不持久化第二套进度 digest。
10. bundled `pi-subagents 0.64.0` 同时提供公开 API 和唯一 runtime owner；零 owner、多 owner、public preflight 前后不一致，或 terminal 的真实 run ID、agent、model、thinking、runtime digest 无法证明时，在相应权限或结果边界失败关闭。
11. 开发阶段按复杂度、风险和不确定性自适应。
12. 验收由 runtime gates、按路径要求的 fresh review 和用户验收共同构成；Tiny 默认不要求 reviewer。
13. Package 不训练模型、不自主修改自身、不自动上传数据。
14. Package 不自动 commit、push、创建 PR、发布或部署。
15. 项目 `AGENTS.md`、事实源和唯一计划台账始终优先。
16. Extension 在每个可证明状态边界持久化运行时断点；项目进度只在 writer-free 边界按项目规则及时回写，断线后从最后可证明断点和证据继续。
17. 用户界面和状态命令使用中文主标签并保留英文枚举；持久化与 API 只使用稳定英文状态值。
18. 用户界面和文档使用中文角色名称并保留英文角色标识；Agent 发现、配置和编排只使用稳定英文标识。
19. writer-free 项目进度回写使用 path/command 受限的临时 progress-sync 控制面权限，结束后恢复原状态并释放 lease。
20. approve、resume 和强制释放 lease 等所有可能放宽权限的动作，只接受交互式 TUI 中的实际用户确认，其他来源失败关闭。
21. 技术方案先用大白话对齐最终效果、非目标、关键场景和可执行验收，再说明技术实现；实施计划不得偏离这些已批准内容。
22. review 使用集中发现、可验证关闭义务、批量返工和一次 closure review；同类 P0/P1 重复出现时返回设计阶段，而不是无限 review/fix。
23. Standard/High-Risk 批准 solution 后立即 create-only 同步技术方案，批准 plan 后只同步实施计划；兼容 plan-v2 combined 路径一次创建两份。两份文档成功并记录摘要前不得进入源码实现，方案修订只覆盖摘要仍匹配的 Package 写入版本；Tiny 不进入文档同步逻辑。
24. TUI 用户批准 solution/plan 后，无需再次输入非决策命令；Package 在聊天区显示当前动作并自动进入 plan/run，失败时保留可手工恢复入口。
25. 机器 marker 与 JSON contract 只保留在 Session 原始协议中，TUI 和落盘需求文档默认隐藏；显示层不得改变批准与恢复事实。
26. 面向 AI/runtime 的协议、状态和诊断保持稳定英文；面向用户的 TUI 状态、断点、下一步、阻塞原因、证据和确认字段统一使用中文主文案。
27. Delivery 工具按当前状态分阶段开放；同进程 reload 复用进入流程前的原始 Pi 工具基线，当前阶段必需工具缺失时失败关闭，并由只读 runtime status 明确说明下一步。
28. `delivery_invalidate(target=BLOCKED)` 只形成保留批准链、规划文档、candidate/evidence 和 `resumeState` 的临时阻塞；真正撤销批准必须明确选择 `SHAPING` 或 `PLANNING`。
29. TUI 用户确认 `/delivery-resume` 且恢复状态、必要 lease 和策略提交成功后，Package 自动展开当前阶段的 plan/run；取消、非 TUI 或任一步失败时零自动续跑。
30. Standard/High-Risk plan 批准前使用 pi-subagents 公开 preflight 证明 builtin reviewer 至少有一个可用 candidate；失败时保持待批准和只读，不启动 child 或调用 Provider。Tiny 不执行 reviewer preflight。
31. 固定验证不启动 AI child；Delivery Gate 只通过 Pi 公开 `pi.exec` 顺序执行已批准命令，在当前工具调用中显示进度，并保存绑定 candidate 的逐命令终态摘要。
32. Tiny 和兼容的 plan-v2 `single` 路径允许父 Pi 直接写；Tiny 额外执行 exact path guard 和 baseline delta proof。`standard/high-risk` 从父 Pi 移除源文件写工具，只允许一个 builtin fresh foreground worker，在匹配 terminal run ID 与 `launchContractDigest` 后自动冻结 candidate。
33. Tiny 保留 single writer、lease、TUI authorization、baseline、candidate freeze、runtime validation、evidence binding、stale detection 和 fail-closed；scope 扩大必须立即降权到 `SHAPING`，保留 partial diff 并重新走 Standard/High-Risk 批准。
34. Standard/High-Risk reviewer 必须收到与 current candidate 对应的有界 actual diff，并返回绑定 candidate/diff digest 的结构化结果；bare verdict 不构成 review evidence。
33. 固定命令失败不自动等同于源码缺陷；父会话必须区分候选代码、验证环境和已批准计划，只有代码问题进入返工，计划错误重新批准。
34. `adaptive-delivery` 内置按需方案追问：先查项目事实，每次只问一个高影响决策并给推荐答案；极小且明确的需求零追问，全部关键歧义关闭后立即成案。
35. 技术方案按任务结构生成最多 1 至 3 张有帮助的 Mermaid 图；Package 保证六类图在支持图片的 TUI 中自动显示 PNG，在其他终端显示字符回退，同时原始 Session 和 Markdown 始终保留 Mermaid 源码。
36. 已同步两份规划文档后的同路径修订，只能覆盖 runtime evidence 绑定且现场摘要与身份未漂移的 Package 文档；外部修改继续失败关闭。
37. builtin worker 不获得通用 shell；可选确定性修复命令必须来自已批准 plan contract，并由 Delivery Gate 在唯一 writer lease 内、candidate freeze 前执行。
38. `delivery_begin` 只在 `IDLE` 可见，非 `IDLE` 状态只暴露当前阶段合法工具与只读状态/降权入口。
39. 固定验证在 TUI 中隐藏默认高频 working spinner并使用低频 Package heartbeat；显示控制不得改变命令 timeout、终态和 evidence。
40. `setActiveTools` 负责模型路由但不是唯一授权边界；provider payload 按当前阶段允许列表过滤，`tool_call` 执行前拒绝最后一次成功阶段策略集合外的任意工具，内置项目写工具还必须按当前 state、route、实时 approval/lease 与 scope 失败关闭。
41. `delivery_progress_sync` 只在拥有已批准 plan/progress target 且无 runtime writer lease 的 `VALIDATING` 或 `BLOCKED` 暴露；target 必须是 canonical project-relative 非保留路径，exact `oldText/newText` 均非空，execute 仍要求 workspace 无其他 writer、可证明 lease 和固定写后检查，取消或 `killed` 不能被退出码 0 覆盖。
42. SHAPING/PLANNING 的父 Pi 文件读取具有单次和单 agent run 上限；该上限只约束取证体量，不替代搜索、事实判断或用户批准。
43. validation timeout 必须依据同环境耗时证据并保留余量；外部子进程的终止边界属于批准命令本身，runtime 对 `killed` 的 timeout 结果继续失败关闭。
44. 每个低层 agent、provider 请求、父源码写工具和 worker 启动边界都必须重新证明适用的 planning approval/document identity 与 canonical writer lease；缓存字段只用于状态展示，不构成持续授权。
45. Session 恢复遇到终态未知的 worker 时保留 lease 并保持只读；`/delivery-resume` 在重新开放阶段前复验未知 worker 和已有 evidence，恢复 `VALIDATING` 还必须证明现场 candidate 未变，恢复 `REWORKING` 则允许批准范围内的部分返工现场，任何适用证明失败都继续 `BLOCKED`。
46. 只有 `BLOCKED` 可以携带 `resumeState`；`DELIVERED` 持久状态必须具有一致的批准、candidate、passed validation、适用 review/Tiny scope 和 final evidence。
47. Standard/High-Risk worker 不得修改 solution、plan 或任何 `progressTargets`；Package 必须在 worker terminal 后、repair 前以及 repair 后、candidate 前复验这些受保护制品，漂移时失败关闭且不形成候选。公开委派能力不描述为路径级操作系统沙箱。
48. 已处于 `BLOCKED` 时再次发生 runtime proof failure 必须保留原 `resumeState`；实时 worker 进度只用于有界展示，不持久化也不影响授权事实。
