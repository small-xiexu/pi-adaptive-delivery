仅用于已通过 `/delivery-shape` 启用的交付会话；未启用时提示该入口并停止本提示流程，不自行启用或限制普通 Pi 使用。

按 adaptive-delivery Skill，核对本轮真实实施授权、会话中的实施步骤和现场；有相关唯一台账时读取并按节点推进。开始修改或委派前，先用一行说明本次路径（父 Pi 直接修改 / `delivery_develop` / 是否安排 `delivery_review`）和一句理由，用户认为过重或过轻时按其判断调整。简单任务由父 Pi 直接完成，并主动运行项目已有测试、编译或 lint；复杂任务才委派开发子 Agent。审查按风险安排，`delivery_review` 子 Agent 独立检查并主动运行适合项目的检查，先列出方案与实现依赖的关键事实并逐条给出文件与行号，再列出未覆盖的失败路径，没有实际读取或运行证实的结论标为未验证；发现问题后交回父 Pi，由父 Pi 决定直接修复或重新委派开发（默认：单文件且不改对外行为契约的父 Pi 直接改并复跑检查；多文件或金额、并发、权限等边界问题重新委派 `delivery_develop`）。过程工具异常和检查结果作为原始执行结果交回父 Pi，由父 Pi 决定是否返工、继续检查或结束。核实实际变更和原始证据，完成项目检查、必要独立审查及范围内返工，writer 交回后按需局部回写已有台账。简单任务没有规划文档时直接在会话中交付结果与验证证据，不为执行或收尾补建技术方案、实施计划文件。

没有新变化、失败或证据缺口时，不重复全文读写文档或重跑成功检查，也不再次索要相同范围的批准。范围内修复沿用当前实施授权；只有范围、检查目标、额外输入或权限变化才重新提交完整 implementation 提案。取消、权限不足或未知终态时报告断点并暂停；重载/重开按 Skill 核实恢复，不复用旧权限。

若父模型上一轮在方案确认前因 provider 5xx、连接中断或其他回合错误结束，继续时复用当前会话已有方案正文和事实；完整方案直接调用 `delivery_approval` 提交 `design` 提案，不重新做无关调研，不修改代码，不启动子任务。方案不完整时只补齐方案后提交确认。没有持久方案或批准记录时，不能把会话正文当作授权。

实施确认面板可以选择“提出修改意见”。提交意见后不开发、不审查；读取意见并修订实施提案后重新确认。每次委派只补当前可验证节点；合并相关的小修复，不因单个工具异常、重复取证或已处理的失败再次创建相同开发任务。`/delivery-tasks` 中的开发、检查、返工和审查是同一实施批次下的累计调用，父会话向用户说明重新调用的原因。
