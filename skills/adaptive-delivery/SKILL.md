# 自适应交付

本 Skill 只约束已通过 `/delivery-shape` 启用的交付任务。安装 Package、普通自然语言需求或单独读取本文件均不启用交付；未启用时继续 Pi 原来的工作方式，不要求补做交付确认。`/delivery-status` 可查看是否启用。启用记录只保留流程选择，不授予方案或实施权限；任务收尾后由用户 `/delivery-exit` 退出并恢复原工具，不能把退出当作验收通过。

## 需求对齐

先读项目规则和已有相关方案/唯一进度台账，再核实相关代码、测试与运行事实。简短说明对当前需求的理解，区分已知事实与假设。能从项目查明的内容自行核实，不让用户代查 API 或排查代码。普通问答不自动修改文件；确需维护文档时，Markdown 编辑默认允许，无须另行请求文档授权。

- 先判断不同回答是否会明显改变本次交付的效果、范围或关键取舍；只追问有依据、尚未解决且需要用户决定的问题。技术实现细节自行查证；推测性的边缘场景和未来扩展留待实际需要，不据此扩大当前范围或延长讨论。
- 每轮只提出一个需要回答的关键问题，给出简短背景、推荐答案及理由，然后等待回答。不一次列出全部问题，也不把多个独立决定塞进同一个问题。用户说“按推荐”仅接受当前问题的推荐，不代替方案或实施批准。
- 收到回答后先更新理解与方案，再判断是否需要下一问；跳过已被回答覆盖的问题，只继续处理仍影响当前交付的关键不确定性。用户纠正或改变方向时立即调整后续讨论，不沿预设问卷继续盘问。
- 效果、范围、主要场景和验收已清楚时停止追问，整理简短方案，说明已确定的行为和采用的假设；一开始就清楚的需求可以零追问。关键业务取舍仍未确定时不能用默认假设跳过；非关键技术细节在授权范围内自行决定，不逐项请用户确认。
- 不规定最少或最多轮数，不追求穷尽所有可能性。用户仍想讨论时围绕其关注点继续；用户准备确认时衔接阶段确认，不重新询问已决定的事项。

## 文档按需

简单明确、范围局部、可一次完成并验证的任务，直接在会话中简短说明方案、实施步骤和验证方式，不强制创建技术方案或实施计划文件。需要持续查阅设计决策、跟踪多个依赖步骤或分阶段交付时再落文档；已有方案/台账按项目规则沿用并按需更新，不为每个小步骤额外新建两份文件。

判断依据是实际风险、不确定性和持续维护需要，不按改动行数评分，也不引入固定任务模式。简短说明采用的安排即可，不增加“是否写文档”的例行确认。用户或项目明确要求文档时遵循其要求；没有文档时，方案/实施正文和执行证据保留在原生会话中，不伪造文档路径或为填参数创建占位文件。

## 阶段确认

父 TUI 的 `delivery_approval` 分别记录以下确认；正文按本次决策写清楚，不复制全文台账或用文件路径、摘要 ID 代替内容：

- `design`：`paths` 列明本任务由父维护的确切规划 Markdown 路径（技术方案、唯一台账等），随确认冻结并禁止子修改；这不是文档写入授权。没有规划文档时传 `[]`。正文先用大白话说明这次改成什么，再说明范围、关键设计、验收方向和必要取舍；有文档时在后面补充修改摘要，路径由界面详情列出。不得遗漏已有需维护的方案/台账，也不为填路径创建文件。
- `implementation`：正文先给出实际步骤、依赖、本机工具链与停止条件，参数明确文件工具实际可写范围、固定验收命令及额外验收输入 `inputs`。界面直接列出范围和命令，正文无须重复相同清单；需要时说明计划目标文件与授权目录的区别。不要把目录授权说成只允许几个目标文件，也不把路径声明说成对 Shell 的隔离。工具的详情可查看已批准方案原文，不再把同一份方案抄入实施正文。

按文档需要整理方案草稿，可供审阅时用 `design` 打开底部输入区，让用户查看方案正文、提出意见或明确确认。简单任务直接审阅会话正文；需要文件时使用父文档工具落盘，不调用 `documents` 阶段或再询问编辑权限，不因草稿已写好就催促批准。方案确认后准备实施步骤与验收说明，用户准备确认时申请实施，获批后才开发。两次阶段确认不合并，简单任务的两份正文均可留在会话中。确认成功且没有未决问题或暂停要求时直接衔接下一阶段，不再等待不承载决策的“继续”。模型、子 Agent、工具结果、摘要或旧 Session 不能代替本轮可信批准。

- 收到审阅输入框或普通对话中的修改意见后，结合最新会话正文与现场修订方案；有方案文件时先读取用户改动并修订同一份文件。必要时一次只追问一个关键问题，不把反馈当作拒绝、批准或实施授权。
- 修改后说明改了哪里、未采纳的意见及理由，再按最新方案生成新的 `design` 提案继续审阅。不能直接批准上次正文，也不进入详细计划或源码开发；循环直到用户明确选择“确认方案”。
- 用户选择“提出修改意见”后打开输入框，Enter 发送、Shift+Enter 换行，输入中的 Esc 只返回方案页。在方案页选择“稍后再看”或按 Esc 才暂停本次审阅；工具返回暂停后停止推进，不自动再次弹出。方案和已发送讨论保留，普通输入恢复；用户之后说“继续看方案”、直接提意见或使用 `/delivery-resume` 都可继续讨论。恢复时核对会话正文、已有意见及现场，有文件时读取最新内容；只恢复审阅，不自动批准或开始实施，也不因恢复补建规划文件。
- `/delivery-resume` 定位当前会话当前分支最近未确认的方案；没有记录则提示，无须猜测另一会话。重载或重新打开原 Session 后，讨论与默认 Markdown 编辑可继续；旧方案/实施批准及验收不恢复，开发前重新取得本轮确认。未知 writer 保持关闭，不用试写探测。实施阶段拒绝或取消仍暂停，不自动重问。

## 子任务模型与推理级别

所有子任务固定使用父 Pi 当前的 Provider 和模型，只按本次工作目的、复杂度和风险选择推理级别。父 Pi 切换模型后，新启动的子任务跟随切换，已启动的任务保持原模型。当前模型支持的级别会随本轮交付提示提供；没有指定级别时继承父当前级别，不猜测其他模型或配置认证。

| 工作场景 | 建议起点 | 调整依据 |
|---|---|---|
| 需求澄清 | medium | 复杂业务规则与关键取舍用 high |
| 现状调研与取证 | medium | 明确查找用 low，跨模块推导用 high |
| 技术方案设计与编写 | high | 简单局部方案可用 medium |
| 技术方案审查 | high | 特别困难的关键边界按需 xhigh |
| 实施计划编制 | medium | 复杂依赖、迁移和验证安排用 high |
| 代码编写 | medium | 并发、权限、事务及跨模块变更用 high |
| 测试设计与编写 | medium | 复杂状态、时序及故障注入用 high |
| 代码审查 | high | 机械修改可用 medium，困难边界按需 xhigh |
| 测试执行与验收 | low | 覆盖充分性与结果分析用 medium/high |
| 故障定位与返工 | high | 根因明确的局部修复可用 medium |
| 配套文档编写 | medium | 已确认事实的机械同步用 low |
| 文档审查 | medium | 涉及设计合理性或事实冲突用 high |
| 交付与发布 | medium | 固定步骤用 low，迁移/回滚设计用 high |
| 运行维护 | medium | 常规巡检用 low，复杂排障用 high |

上述是判断指引，不是必须走完的固定阶段或 14 个固定角色。业务判断、方案/计划编写和 Markdown 更新继续由父负责；子配置只作用于本次委派，不改变父模型或授予额外权限。审查技术方案与文档可使用 `delivery_readonly`；候选代码审查使用 `delivery_review`，仍需要可信验收。

四类委派均可传 `agent: { thinking, reason }`；`thinking` 可省略，`reason` 用一句话说明场景与选择依据，不接受单独指定模型。xhigh 仅在父模型支持且任务确实困难时使用；不支持推理的模型使用 off。工具失败先取证，缺资料或缺环境应解决实际缺口，不靠提高级别或重复委派碰运气。卡片显示实际模型/级别，详情可看理由；不建立费用、token 或性能统计。

## 文档与证据

需要文档时，篇幅随任务调整：方案记录决策和必要事实，唯一台账记录步骤、当前状态与证据索引，README 面向实际使用。不在多份文档重复维护执行进度，不为既有项目新增第二份 TODO 或 JSON 任务树。已有台账按可验证节点及时局部回写，父项未全部验证时保留进行中或阻塞状态；无文档简单任务直接在会话中说明结果和必要证据，不为交付报告补建台账。

已有文件修改前读取当前内容并保留用户改动；用 `delivery_document_write` 创建，`delivery_document_edit` 局部修改。每回合只发起一次文档变更，等待原生终态和 writer 交回后继续。核对修改处及其影响；没有新变化、截断或矛盾时，不反复全文读回所有文档。进度更新不能替换批准依据或扩大权限。

父会话仍须核对实际变更、命令结果和审查发现。按工具返回的路径定位相关原始输出、终态或审查正文；信息缺失、内容截断、前后矛盾或现场变化时补充读取，不把子总结当作证据，也不为复述已核实事实反复遍历整份 Session。原生终态与批准核验始终由工具执行，已读内容不能缓存成权限。

普通只读、开发或审查返回“已结束，有工具错误待核对”时，只能确认本次委派正常结束，不能据此宣称错误已修复或任务已验收。按原记录核对工具错误、后续操作及最终产物；仍有问题就在原授权内返工，已有充分修正证据则继续必要验证，不因一次历史错误盲目重跑整项委派。原始错误必须保留；固定验收失败、用户取消和未知终态仍按原规则处理。

长 JSONL 的 grep 匹配行可能在 500 字符处截断，仅适合定位记录。原生与 Structured 交付环境都使用 `read` 按行读取原始记录；输出截断时按工具提示继续读取，不把截断的行当成完整证据。仍无法取得所需原文时明确报告缺口，不借用父 Shell 绕过只读边界。失败后可能只有报错前正文，不能假定最后一条 assistant 就是完整结论，也不能把重新审查当成读回原证据。

开发自检不替代固定验收。首次执行就保留实际结果；若只缺退出码或摘要，先定位已有原生记录，不为给成功测试补一行说明而重跑。实现或验证条件变化、失败或确有证据缺口时才复验，未运行/失败/取消须如实说明。

## 执行与交付

用户在父 TUI 手动输入的 `!` / `!!` 保留 Pi 原生 Shell 行为，无须方案或实施确认；这是用户直接操作，不是模型可调用的宿主执行工具。不要要求用户为手动命令补做交付批准，也不引导模型借此执行命令。人工输出不代替固定验收；用户修改文件后按实际候选核验，原始记录不产生新权限。

当前提供原生与 Structured 两种环境的读取工具、父分阶段批准与 Markdown 编辑、本机开发、固定候选验收和独立审查。`delivery_readonly` 使用 `read/grep/find/ls` 及已核实的图片读取，不开放通用 Shell。任务提供目标、必要背景、边界与预期证据，不冒充完整环境重建。

Structured 进入交付时补回 Pi 原生读取工具；父与只读/审查子可读取本机源码、规则、Skill、原始 Session 及审查制品（`before/after/diff.patch`），但不能调用 `exec_command/write_stdin/apply_patch`。开发子使用已核实插件的本机命令与补丁能力，参数及输出预算沿用该插件。命令返回 `session_id` 后，必须用 `write_stdin` 取回最终退出，不能把仍在运行的命令当作完成。

`delivery_develop` 自动附带已批准方案、实施正文、路径与命令；`task` 只补本节点目标、现场事实和预期证据，不复制父历史或再次重述批准全文。按实际风险和可验证片段安排委派，不设固定团队。子不修改父规划文档、不请求批准、不继续委派。

实施确认后，命令直接在本机项目目录运行，使用当前用户的 Shell、工具链、文件和网络权限。文件工具继续检查 `paths` 和受保护路径；Shell 不受这些路径隔离。遵守批准范围，不擅自安装依赖、访问外部系统、修改执行记录或遗留后台服务。缺少项目依赖时说明缺口，按用户授权处理；不要求安装 Docker 或准备镜像。

原生 `bash` 的时限与取消沿用 Pi 本机执行语义；测试耗时未知时不随意缩短 `timeout`。失败先读实际退出码、时限及输出；输出截断或终态未取得须如实说明，不把超时或取消当作通过，不自行改写冻结命令。工具返回只能证明本次受控调用交回，不能证明任意脚本脱离管理的后台后代都已消失。

文件工具禁止改动父规划文档、Git、父子 Session、链接和批准范围之外的路径；可在批准路径内创建新文件。工具、基线/制品或交互不足时报告具体缺口，不伪造 formatter 或验证结果。普通子 `select/confirm/input` 可经父 TUI 回答，但不授予阶段权限；拒绝、取消、超时或交互失败暂停任务。非 TUI、并发问题及多行 editor 不支持。

用 `delivery_validate` 在本机执行原批准命令清单。缺命令、漏跑、非零退出、取消或候选变化均不是通过；候选包含明确源码及额外输入的内容和元数据、cwd、本机平台信息与命令，不按 Git ignore 排除范围内文件。候选不是整台电脑或全部依赖的快照；固定验收中不修改源码或验收输入，临时输出放系统临时目录。

按风险使用 `delivery_review`，`task` 只补审查重点和盲点；工具自动提供原批准正文、代码路径、实际差异和原始验收记录。父核对发现并裁决，“审查结束”不等于无问题。明确失败可在原授权内返工，修改后重新验收/审查。子执行实际收尾、父原生结果落盘并取回 writer 后，再按需回写已有台账或直接交付；未知清理或记录状态禁止新写入。

交付说明实际文件、用法、验证结果、兼容性、限制与未执行项，引用必要证据，不重抄全过程。不得自动提交、推送、创建 PR、安装、发布或部署。

## 中断恢复

重载或中断后核对原始会话中的方案、实施正文与执行证据，有相关方案/唯一台账时读取最新内容，再核实现场，查看 `/delivery-status` 的磁盘 lease 并定位子执行。没有足够记录时说明缺口，不猜测原任务或为恢复补建文件。正常收尾不自动续跑，旧方案/实施批准和验收不从日志或摘要恢复，开发前重新确认。任务内 Markdown 编辑默认允许；未知 lease 或工具终态仍阻止写入，不自动解锁、重放或回滚部分结果。
