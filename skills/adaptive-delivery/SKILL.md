# 自适应交付

本 Skill 只约束已通过 `/delivery-shape` 启用的交付任务。安装 Package、普通自然语言需求或单独读取本文件均不启用交付；未启用时继续 Pi 原来的工作方式，不要求补做交付确认。小改动、低风险、范围明确的任务可以直接使用普通 Pi；涉及多个文件、业务行为、接口、权限、迁移、复杂测试或独立检查时，再使用 `/delivery-shape`。`/delivery-status` 可查看是否启用。启用记录只保留流程选择，不授予方案或实施权限；任务收尾后由用户在状态面板明确选择“结束交付”，恢复原工具，不能把退出当作验收通过。

## 需求对齐

先读项目规则和已有相关方案/唯一进度台账，再核实相关代码、测试与运行事实。简短说明对当前需求的理解，区分已知事实与假设。能从项目查明的内容自行核实，不让用户代查 API 或排查代码。普通问答不自动修改文件；确需维护文档时，Markdown 编辑默认允许，无须另行请求文档授权。

- 先判断不同回答是否会明显改变本次交付的效果、范围或关键取舍；只追问有依据、尚未解决且需要用户决定的问题。技术实现细节自行查证；推测性的边缘场景和未来扩展留待实际需要，不据此扩大当前范围或延长讨论。
- 每轮只提出一个需要回答的关键问题，给出简短背景、推荐答案及理由，然后等待回答。不一次列出全部问题，也不把多个独立决定塞进同一个问题。用户说“按推荐”仅接受当前问题的推荐，不代替方案确认。
- 收到回答后先更新理解与方案，再判断是否需要下一问；跳过已被回答覆盖的问题，只继续处理仍影响当前交付的关键不确定性。用户纠正或改变方向时立即调整后续讨论，不沿预设问卷继续盘问。
- 效果、范围、主要场景和验收已清楚时停止追问，整理简短方案，说明已确定的行为和采用的假设；一开始就清楚的需求可以零追问。关键业务取舍仍未确定时不能用默认假设跳过；非关键技术细节在授权范围内自行决定，不逐项请用户确认。
- 不规定最少或最多轮数，不追求穷尽所有可能性。用户仍想讨论时围绕其关注点继续；用户准备确认时衔接阶段确认，不重新询问已决定的事项。

## 文档按需

简单明确、范围局部、可一次完成并验证的任务，直接在会话中简短说明方案、实施步骤和验证方式，不强制创建技术方案或实施计划文件。需要持续查阅设计决策、跟踪多个依赖步骤或分阶段交付时再落文档；已有方案/台账按项目规则沿用并按需更新，不为每个小步骤额外新建两份文件。

判断依据是实际风险、不确定性和持续维护需要，不按改动行数评分，也不引入固定任务模式。简短说明采用的安排即可，不增加“是否写文档”的例行确认。用户或项目明确要求文档时遵循其要求；没有文档时，方案/实施正文和执行证据保留在原生会话中，不伪造文档路径或为填参数创建占位文件。

## 阶段确认

父 TUI 的 `delivery_approval` 只记录一次方案确认；正文按本次决策写清楚，不复制全文台账或用文件路径、摘要 ID 代替内容：

- `design`：`documentStrategy` 明确传 `none`（不落盘）、`reuse`（复用现有文档）或 `new`（新建需求文档）；`paths` 列明本任务由父维护的确切规划 Markdown 路径（技术方案、唯一台账等），随确认冻结，子须遵守不修改这些文档的要求；`technicalPlanPath` 和 `implementationPlanPath` 在适用时必须同时出现在 `paths` 中。策略为 `none` 时传 `paths=[]`，不得为填路径创建文件。正文开头用大白话概括本次修改及效果，多个改动用短条目，再说明范围、关键设计、验收方向和必要取舍；具体测试命令和迁移条件放在相应细节中，不用长段落混写。恢复任务时先核对已有方案、台账和现场，明确哪些内容沿用、哪些内容变化，不推断“范围不变”，也不把重新确认变成重复需求访谈。路径由界面详情列出。不得遗漏已有需维护的方案/台账，也不为填路径创建文件。正文结尾固定另起一行「本次假设：」，列出你依赖、但用户尚未明确确认、且若不成立就要改方案的推断（接口行为、调用范围、兼容要求等，最多 3 条），确实没有就写“无”；这行是给用户当场否决用的，不是形式要求。
- 方案确认按钮显示“确认方案并开始实施”。确认后 AI 在内部拆解并持续更新实施计划，文件数量、任务步骤、执行顺序和范围内返工不再要求用户确认。每次 `delivery_develop` 和 `delivery_review` 调用提供当前 `paths` 与 `inputs`；`paths` 只填本节点源码、测试或配置，`inputs` 只填额外只读证据；与父维护规划文档重叠时在子 Session 启动前拒绝并报告冲突路径。这些参数是本次候选和 writer 交接的任务范围，不是普通 Shell 的隔离。

按文档需要整理方案草稿，可供审阅时用 `design` 打开底部输入区，让用户查看方案正文、提出意见或明确确认。简单任务直接审阅会话正文；需要文件时使用父文档工具落盘，不调用 `documents` 阶段或再询问编辑权限，不因草稿已写好就催促批准。用户确认方案后立即开始实施，AI 内部维护计划并按复杂度直接修改或委派开发，按风险安排审查。没有第二次实施确认，也不把模型、子 Agent、工具结果、摘要或旧 Session 当作本轮方案批准。

- 收到审阅输入框或普通对话中的修改意见后，结合最新会话正文与现场修订方案；有方案文件时先读取用户改动并修订同一份文件。必要时一次只追问一个关键问题，不把反馈当作拒绝、批准或实施授权。
- 方案确认支持“提出修改意见”。意见表示需要调整目标、数据行为、范围、关键设计或验收标准；提交后不开发，父会话修订方案后重新确认。范围内返工和检查复验沿用本轮方案确认；只有上述业务条件或重大外部风险变化才重新确认。
- 修改后说明改了哪里、未采纳的意见及理由，再按最新方案生成新的 `design` 提案继续审阅。不能直接批准上次正文，也不进入详细计划或源码开发；循环直到用户明确选择“确认方案”。
- 用户选择“提出修改意见”后打开输入框，Enter 发送、Shift+Enter 换行，输入中的 Esc 只返回方案页。在方案页选择“稍后再看”或按 Esc 才暂停本次审阅；工具返回暂停后停止推进，不自动再次弹出。方案和已发送讨论保留，普通输入恢复；用户之后说“继续看方案”或直接提意见即可继续讨论。恢复时核对会话正文、已有意见及现场，有文件时读取最新内容；只恢复审阅，不自动批准或开始实施，也不因恢复补建规划文件。
- 用户说“继续”时，先核对本会话当前分支已有方案、修改意见、实施进度、回合状态和当前现场。以本轮提示的真实确认状态为准：确认有效且原执行已收尾时继续剩余工作；确认失效时复用已有方案和证据提交必要的新确认，不重做已明确的需求访谈。没有记录则说明缺口，不猜测另一会话。重载或重新打开原 Session 后，讨论与默认 Markdown 编辑可继续；旧方案确认及验收不恢复，开发前重新取得本轮确认。恢复核对必须在本轮方案确认核验之后进行：开发和审查先核验参数、路径范围、原生调用及活动任务；父文档 writer 使用同一恢复前置。完整证明任务已结束、持久收尾完整、父结果唯一落盘且 workspace 完整身份、owner/coordinator、Session、执行 ID、run ID 和 lease ID 匹配的已知失败，会重新读取原生结果后自动清理同一 lease 并继续；残留 operation lock 需要明确选择，清理顺序先处理 operation lock，再删除 lease，部分失败保留仍可核对的现场。进程强杀、扩展异常、记录不完整或归属不一致时保留现场，只显示一次“恢复交付”选择。未知 writer 保持关闭，不用试写探测，不把清理当成成功或旧批准恢复。实施阶段拒绝或取消仍暂停，等用户表达继续意图再推进。

模型请求在方案确认前因 provider 5xx、连接中断或其他父回合错误结束时，下一轮先复用当前会话中已经形成的方案正文和事实，不把错误当作批准，也不重复无关取证。若正文已经足够完整，直接用同一范围、文档策略和验收意图调用 `delivery_approval` 提交新的 `design` 审阅提案；若正文不完整，只补齐方案后再调用该工具。没有 `delivery_approval` 的持久提案或确认记录时，不得启动开发、验收或自动批准；半截模型输出只能作为草稿，不能替代持久方案记录。`/delivery-status` 显示的下一步是恢复提示，不代表方案已经提交或确认。

## 子任务模型与推理级别

所有子任务固定使用父 Pi 当前的 Provider 和模型，只按本次工作目的、复杂度和风险选择推理级别。父 Pi 切换模型后，新启动的子任务跟随切换，已启动的任务保持原模型。当前模型支持的级别会随本轮交付提示提供；没有指定级别时继承父当前级别，不猜测其他模型或配置认证。

| 工作场景 | 建议起点 | 调整依据 |
|---|---|---|
| 需求澄清 | medium | 复杂业务规则与关键取舍用 high |
| 现状调研与取证 | medium | 明确查找用 low，跨模块推导用 high |
| 技术方案设计与编写 | high | 简单局部方案可用 medium |
| 技术方案审查 | high | 特别困难的关键边界按需 xhigh |
| 实施计划编制 | medium | 复杂依赖、迁移和验证安排用 high |
| 代码编写 | medium | 并发、权限、事务及跨模块变更用 high |
| 测试设计与编写 | medium | 复杂状态、时序及故障注入用 high |
| 代码审查 | high | 机械修改可用 medium，困难边界按需 xhigh |
| 测试执行与验收 | low | 覆盖充分性与结果分析用 medium/high |
| 故障定位与返工 | high | 根因明确的局部修复可用 medium |
| 配套文档编写 | medium | 已确认事实的机械同步用 low |
| 文档审查 | medium | 涉及设计合理性或事实冲突用 high |
| 交付与发布 | medium | 固定步骤用 low，迁移/回滚设计用 high |
| 运行维护 | medium | 常规巡检用 low，复杂排障用 high |

上述是判断指引，不是必须走完的固定阶段或 14 个固定角色。简单任务由父 Pi 直接完成并核对；复杂任务才使用 `delivery_develop`，必要时使用 `delivery_review`。业务判断、方案/计划编写和 Markdown 更新继续由父负责；子配置只作用于本次委派，不改变父模型或授予额外权限。子 Agent 主状态只反映运行中、正常结束或异常退出；工具异常、测试结果和收尾细节作为原始执行结果交回父 Pi，不单独提升为主状态。任务详情额外显示调用前范围校验、批准/候选准备、子 Session 启动、子 Agent 工具执行、子 Session 收尾和父结果/writer 交接阶段；审查候选变化、模型终态、退出信号、工具失败、在途工具和 Session 持久化不能被自然语言总结覆盖。审查技术方案与文档可使用 `delivery_readonly`；候选代码审查使用 `delivery_review`，由父核对其实际检查结果。父 Pi 直接实施源码或测试节点前，先调用 `delivery_path` 记录 `parent_direct`、节点、理由和是否计划独立审查；委派路径由 Package 根据真实调用自动展示。该记录不代表代码完成或检查通过。

四类委派均可传 `agent: { thinking, reason }`；`thinking` 可省略，`reason` 用一句话说明场景与选择依据，不接受单独指定模型。xhigh 仅在父模型支持且任务确实困难时使用；不支持推理的模型使用 off。工具失败先取证，缺资料或缺环境应解决实际缺口，不靠提高级别或重复委派碰运气。卡片显示实际模型/级别，详情可看理由；不建立费用、token 或性能统计。

## 文档与证据

需要文档时，篇幅随任务调整：方案记录决策和必要事实，唯一台账记录步骤、当前状态与证据索引，README 面向实际使用。不在多份文档重复维护执行进度，不为既有项目新增第二份 TODO 或 JSON 任务树。已有台账按可验证节点及时局部回写，父项未全部验证时保留进行中或阻塞状态；无文档简单任务直接在会话中说明结果和必要证据，不为交付报告补建台账。

已有文件修改前读取当前内容并保留用户改动；用 `delivery_document_write` 创建，`delivery_document_edit` 局部修改。每回合只发起一次文档变更，等待原生终态和 writer 交回后继续。核对修改处及其影响；没有新变化、截断或矛盾时，不反复全文读回所有文档。进度更新不能替换批准依据或扩大权限。

父会话仍须核对实际变更、命令结果和审查发现。按工具返回的路径定位相关原始输出、终态或审查正文；信息缺失、内容截断、前后矛盾或现场变化时补充读取，不把子总结当作证据，也不为复述已核实事实反复遍历整份 Session。原生终态与批准核验始终由工具执行，已读内容不能缓存成权限。

普通只读、开发或审查的过程工具异常只保留在原始 Session 和详情中，不改变子 Agent 的运行中/已完成/异常退出主状态；任务详情另显示当前执行阶段和父侧失败事实。先依据原始记录核对具体原因、后续操作及最终产物；摘要缺失或截断时按行号读取原文。对用户直接说明已确认的原因和影响，例如“检索未找到匹配，相关内容已从实际位置核对”，或“测试仍失败，父 Pi 正在决定是否返工”，不要只复述笼统警告。这样的结论必须有原始证据；退出 1 不能自动认定为搜索无匹配，一次后续成功也不证明此前所有问题已解决。父会话的核对结论写在对话或已有台账，不另建确认记录。仍有问题就在原授权内返工，已有充分证据则继续必要检查，不因历史错误盲目重跑整项委派。用户取消、进程异常和无法取得可信收尾证据才影响子 Agent 主状态。

长 JSONL 的 grep 匹配行可能在 500 字符处截断，仅适合定位记录。使用当前 Pi 已启用的读取工具或 Shell 按需提取原始记录。输出截断时继续读取必要原文，不把截断的行当成完整证据。仍无法取得原文时明确报告缺口。失败后可能只有报错前正文，不能假定最后一条 assistant 就是完整结论，也不能把重新审查当成读回原证据。

开发自检不替代父 Pi 对最终结果的核对，也不替代高风险任务的独立审查。父 Pi 或审查子 Agent 应主动运行项目已有测试、编译或 lint；没有运行不能声称通过。实现或检查条件变化、失败或确有证据缺口时才复验，未运行/失败/取消须如实说明。

## 执行与交付

用户手动 `!` / `!!`、RPC Shell 和模型的普通工具调用均沿用 Pi 及原插件的执行与权限检查，Package 不额外拦截。不要要求用户为手动命令补做交付批准，也不引导模型让用户代跑自己可调用的命令。普通输出不代替实际检查；文件变化后按实际候选核验，原始记录不产生新批准。

开发、审查及分析子 Agent 都继承父 Pi 当前已启用的全部普通工具和原有权限检查，包括文件读写、编辑、Shell、联网和插件工具。审查角色也不禁用 `write/edit`，职责差异通过任务提示词说明，不增加角色权限表、工具包装或联网白名单。需要查最新资料时直接使用现有搜索或网页工具，不把交付流程解释成禁网。子会话按配置重建环境，插件启动结束后再次承接父本轮明确选择的工具列表，再核对完整定义与来源；不复制任意插件内存，不补启父未请求的工具。实际未注册、配置禁用或环境仍无法对齐时说明具体缺口，不静默降级。

`delivery_readonly` 仍要求只分析、查资料和提供证据，不修改文件；`delivery_review` 继承全部普通工具，但职责是独立检查、运行检查和报告问题，默认不修改源码。发现问题交回父 Pi，由父 Pi 决定直接修复或重新委派 `delivery_develop`。这些是职责约定，不是删除普通工具形成的隔离。命令、补丁、图片及输出预算沿用当前 Pi 工具。命令返回 `session_id` 后，使用对应的轮询工具取回最终退出，不能把仍在运行的命令当作完成。

方案确认后，简单任务由父 Pi 直接修改源码并主动调用项目已有测试、编译或 lint；不启动子 Agent。开始修改或委派之前，先用一行说明本次采用的路径（父 Pi 直接修改、`delivery_develop`、是否安排 `delivery_review`）和一句理由；用户认为过重或过轻时按其判断调整，不新增档位字段或状态。复杂任务才调用 `delivery_develop`，每次工具调用显式提供本节点的 `paths` 和 `inputs`；`task` 只补本节点目标、现场事实和预期证据，不复制父历史或再次重述批准全文。按实际风险安排 `delivery_review` 做独立审查；审查子 Agent 不是“表态是否完成”，而是先列出方案与实现依赖的关键事实，逐条到实际代码中核对并给出文件与行号，再列出最可能失败但现有检查未覆盖的路径，只有经实际读取或实际运行证实的结论才写“成立”，其余明确标为未验证。按实际风险和可验证片段安排委派，不设固定团队。子不修改父规划文档、不请求批准、不继续委派。若复杂任务委派在子任务发送前因环境握手失败，必须停止本次源码和测试写入，先核对报错与收尾状态；普通写工具不能替代未成功发送的开发委派。

方案确认后通过交付入口安排开发，命令直接在本机项目目录运行。普通文件、Shell 和联网工具不由 Package 接管，`paths` 是本次节点的任务约定与候选范围，`inputs` 是额外只读证据；父维护规划文档由父会话维护，范围冲突应在调用前修正。正常检索资料可以直接进行；安装依赖、外部写入、修改执行记录或启动后台服务仍须遵守用户授权与项目规则。缺少项目依赖时说明缺口，按用户授权处理；不要求安装 Docker 或准备镜像。

原生 `bash` 的时限与取消沿用 Pi 本机执行语义；测试耗时未知时不随意缩短 `timeout`。失败先读实际退出码、时限及输出；输出截断或终态未取得须如实说明，不把超时或取消当作通过，不自行改写冻结命令。工具返回只能证明本次受控调用交回，不能证明任意脚本脱离管理的后台后代都已消失。

遵守约定修改范围，保留父规划文档、Git 和执行记录；普通工具可用不等于已经得到这些修改的授权。父文档专用工具仍核实明确 Markdown 路径与交付 writer。工具、基线/制品或交互不足时报告具体缺口，不伪造 formatter 或验证结果。普通子 `select/confirm/input` 可经父 TUI 回答，但不授予阶段权限；拒绝、取消、超时或交互失败暂停任务。非 TUI、并发问题及多行 editor 不支持。

完成修改后由当前负责的父 Pi 或 `delivery_review` 根据项目实际情况运行测试、编译或 lint，并记录命令和真实结果。简单任务不启动子 Agent；复杂或高风险任务按需调用 `delivery_review`，它独立检查并给出结论。发现问题后由父 Pi 直接修复或重新调用 `delivery_develop`，不把审查和修复合成同一职责。普通工具结果不能被包装成“通过”，未运行、失败、取消或候选变化都要如实说明；Package 不固定命令，也不把模型口头结论当作运行时证明。

按风险使用 `delivery_review`，`task` 只补审查重点和盲点；工具自动提供原批准正文、代码路径和实际差异。审查子主动运行适合项目的检查并记录结果，父核对发现并裁决，“审查结束”不等于无问题。审查发现默认按影响面选修复方式：**单文件、不改变对外行为契约的修复**由父 Pi 直接改并复跑项目检查；**涉及多文件，或金额、并发、权限、迁移等边界，或需要重新跑子任务自检**的修复重新委派 `delivery_develop`，修改后重新检查/审查。这只是完成方式的选择，不扩大已确认范围，也不新增一次实施确认。子执行收尾、父原生结果落盘并取回交付 writer 后，再按需回写已有台账或直接交付；未知清理或记录状态暂停交付写入，不借普通工具绕过暂停要求。

交付说明实际文件、用法、验证结果、兼容性、限制与未执行项，引用必要证据，不重抄全过程。固定按以下四类信息交付：

```text
修改内容：实际改了什么
检查命令：运行了什么、退出码是什么、结论是什么
独立审查：是否执行、发现什么、哪些问题已处理
限制和未执行项：哪些内容没有验证或仍需关注
```

验证结果必须直接列出实际检查命令、退出码和结论；未运行、失败、取消或证据不足分别说明。没有运行检查时写“未运行”，不能写成“检查通过”。子 Agent 的“已完成”只表示其执行已正常收尾，不能替代父 Pi 对当前候选的检查裁决。不得自动提交、推送、创建 PR、安装、发布或部署。

任务已完成且用户已明确授权本次 Git 提交时，先核实执行已收尾、实际差异和验证证据，再由父使用当前普通 Shell 工具按授权范围提交。已有提交授权不因交付重载而撤销，不为提交现有改动重新申请方案确认，也不将纯 Git 提交交给 `delivery_develop`。普通工具缺失时，说明原因并引导用户在 `/delivery-status` 中选择“结束交付”，恢复进入前工具，然后继续已有授权；退出受阻时先核对原执行，不绕过未知 writer。提交不自动包含推送、发布或新的代码修改。

## 中断恢复

重载或中断后核对原始会话中的方案、内部计划与执行证据，有相关方案/唯一台账时读取最新内容，再核实现场，查看 `/delivery-status` 的磁盘 lease 并定位子执行。没有足够记录时说明缺口，不猜测原任务或为恢复补建文件。正常收尾不自动续跑，旧方案确认和验收不从日志或摘要恢复，通过交付入口开发前重新确认。任务内 Markdown 编辑默认允许；未知 lease 或工具终态仍阻止交付工具写入，不自动解锁、重放或回滚部分结果。普通工具继续沿用 Pi 权限，不能声称本包已关闭其能力。

工具握手不一致时按报错中的缺少、额外启用或定义/来源差异核对环境；READY 已在子启动后承接父本轮工具选择，仍缺少时须核对实际注册与配置，不能反复退出重入便断言已修复。父可能仍运行更新前的插件；单独 `/reload` 保留当前启用列表，不能恢复先前被停用的工具。必要时在执行收尾后由用户通过 `/delivery-status` 选择“结束交付”，恢复原工具并重载；继续开发再 `/delivery-shape`。任务未发送且子进程已正常关闭属于启动失败，错误卡片不代表当前仍持有 writer；交接以实际收尾和状态详情为准。若存在未知或残留占用，父先核对原始记录和在途任务；本轮“继续”会在确认方案后自动判断是否可安全恢复。完整证明原任务已结束、结果唯一落盘且 lease 归属匹配时清理同一残留并保留 `delivery-unlock` 审计；进程强杀、扩展异常、记录不完整、lease ID 不匹配或归属未知时只显示一次“恢复交付”选择，选择“暂不处理”保留现场，选择清理也不恢复旧批准、不重放未知执行。状态面板只展示摘要，lease、PID、Session 和收尾证据通过 `Ctrl+O` 查看；不通过状态面板手动解锁。
